# 아키텍처 개요

> Last Updated: 2026-11-03

전체 뉴스 추천 시스템의 설계와 이 저장소의 실제 구현을 구분합니다. 상세 구조는 `agent-project-reference.md`를 참고합니다.

## 전체 데이터 흐름 [계획]

```text
독자 → 프론트엔드 → 뉴스 백엔드 → 후보 기사와 추천 점수 → 프론트엔드
          │
          └→ 행동 이벤트 → 로깅 서버 → 저장·가공 → 관심사·피처 → 모델 학습
```

실제 백엔드, 로깅 서버, 모델과의 연결은 각 저장소의 구현 및 팀 계약을 확인해야 합니다. 이 그림만으로 완료 상태를 판단하지 않습니다. 정확한 이벤트 필드와 수집 단위는 `docs/contracts/`와 `docs/behavior-collection/`의 최신 합의안을 확인합니다.

## 이 저장소 [현재]

- `src/data.js`와 `src/service.js`는 가상 독자·기사와 샘플 피드 순서를 제공합니다. 추천 근거는 시안이며 학습된 모델의 출력이 아닙니다.
- `src/app.js`는 피드, 카테고리, 기사 상세와 오류·빈 결과 화면을 표시합니다.
- Node 서버는 샘플 피드, 비로그인 방문자 식별·저장, 좋아요 API를 제공합니다.
- 방문자 정보는 로컬 SQLite 또는 Docker `visitor-data` 볼륨에 저장됩니다. Docker Compose는 화면 서버를 실행하며 팀 전체 인프라용 compose와 별개입니다.
- 테스트는 독자별 샘플 결과 차이, 신규 독자 처리, 방문자와 좋아요 동작을 확인합니다.

## 다음 연결 [계획]

- 백엔드 피드를 연결할 때 독자 ID, 기사 ID, 추천 결과 ID, 정렬 근거와 오류 응답을 계약에 명시합니다.
- 행동 이벤트를 수집할 때 노출·클릭·체류의 정의와 단위, 발생 시각, 중복 방지, 전송 실패 처리를 명시합니다.
- 이벤트에서 관심사와 추천 결과까지 추적 가능하게 하되 실제 방문자 식별 정보는 노출하지 않습니다.
- 신규 독자와 이력이 부족한 독자의 피드 방식을 계약하고 실제 입력·출력으로 검증합니다.

## 책임 경계

화면과 브라우저 이벤트는 `frontend`, 기사·뉴스 API는 `backend`, 공용 수집·배포 기반은 `infra`, 데이터 처리·모델은 `data-ml-pipeline`이 담당합니다. 담당 경계를 넘는 인터페이스 변경은 관련 계약과 저장소를 함께 확인합니다.
