# 행동 로그 저장 방식 비교

PostgreSQL을 1차안으로 검토한다. 기존 DB 인스턴스의 로깅 전용 스키마에서 기사 제공 기록과 행동 기록을 관리하면, 로그를 수락할 때 독자와 기사 제공 기록의 관계를 검증하고 재전송도 판별할 수 있다. 기사 API와 같은 인스턴스를 쓰므로 실제 부하를 확인한 뒤 결정한다.

| 방식 | GCS 파일 작성기가 10분간 연결이 끊긴 동안 클릭 100건이 들어온 경우 |
|---|---|
| PostgreSQL | DB에 커밋된 행은 남는다. 작성기가 돌아오면 업로드하지 않은 행을 처리한다. |
| Valkey Pub/Sub | 연결이 끊긴 동안 발행한 메시지는 채널에서 다시 읽을 수 없다. |
| Valkey Streams | Valkey가 정상이고 메시지가 보관 중이면, 작성기가 돌아와 새 메시지를 읽고 미완료 메시지를 다시 가져올 수 있다. |

## PostgreSQL

- **장점.** 클릭 E123을 저장한 직후 브라우저 연결이 끊겨도, 같은 ID와 본문으로 재전송하면 고유 키와 저장 내용을 비교해 이미 받은 기록으로 처리할 수 있다. 같은 ID에 다른 본문이 오면 충돌로 처리한다. 기사 제공 기록을 함께 관리하면 클릭의 impression_id가 해당 독자의 것인지 확인하고 저장하는 작업을 한 트랜잭션에 묶을 수 있다. [PostgreSQL 제약 조건](https://www.postgresql.org/docs/18/ddl-constraints.html)
- **단점.** GCS 업로드가 오래 멈추면 대기 행이 늘어난다. 로그 쓰기와 인덱스 갱신이 몰리면 같은 인스턴스의 기사 조회도 느려질 수 있다. 로깅 쪽 연결 수와 수락량을 제한하고, 업로드를 확인한 행만 보관 정책에 따라 정리한다. [Cloud SQL 운영 가이드](https://docs.cloud.google.com/sql/docs/postgres/operational-guidelines)

## Valkey Pub/Sub

- **장점.** 연결된 대시보드에 방금 클릭한 기사를 바로 표시할 수 있다. 한 건을 놓쳐도 학습용 원본에 영향이 없는 실시간 알림에 적합하다.
- **단점.** 작성기가 메시지를 읽은 직후 GCS에 쓰기 전에 종료되면 채널에서 그 메시지를 다시 가져올 수 없다. 발행 성공은 파일 저장 성공을 보장하지 않는다. 수집 경로가 이것뿐이면 장애 시간대의 클릭이 분석에서 빠진다. [Valkey Pub/Sub](https://valkey.io/topics/pubsub/)

## Valkey Streams

- **장점.** 작성기 A가 메시지를 읽고 GCS에 올리기 전에 종료돼도, 완료 표시가 없는 메시지를 작성기 B가 가져갈 수 있다. 파일 저장을 확인한 뒤 XACK로 완료를 표시한다. 전용 Valkey 인스턴스를 두면 로그 수신의 쓰기 부하를 기사 DB와 분리할 수 있다.
- **단점.** AOF를 1초마다 디스크에 반영하도록 설정하면 장애 직전 일부 기록이 유실될 수 있다. 작성기가 GCS에 올린 뒤 XACK 전에 종료되면 같은 메시지가 다시 처리될 수 있다. 영속화와 복제 설정, 미처리 메시지를 보호하는 보관 정책, event_id 중복 처리, 기사 제공 기록의 소유권 검증이 필요하다. [Valkey Streams](https://valkey.io/topics/streams-intro/), [Valkey 영속화](https://valkey.io/topics/persistence/)

## 적용 전 확인

- 예상 피크만큼 테스트 로그를 넣으며 기사 조회 응답 시간, DB 여유 공간과 연결 수, GCS 업로드를 가장 오래 기다린 로그의 대기 시간을 확인한다.
- GCS 저장은 세 방식 모두 별도 파일 작성기가 담당한다. KST 09:07에 발생한 클릭은 늦게 도착해도 minute=05 경로에 쓴다. 업로드 직후 완료 기록에 실패하는 상황을 재현해 재시도 시 중복 파일이 생기지 않는지 확인한다.
