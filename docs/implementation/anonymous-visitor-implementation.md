# 비로그인 방문자 식별 구현

2026년 10월 29일 구현. 로컬 검증용이며 외부 배포하지 않았다.

## 실제 구현 범위

쿠키에는 32바이트 난수로 만든 표식만 들어간다. 서버 SQLite에는 표식의 SHA-256 해시, 독자 ID, 생성·최근 방문·만료 시각만 저장한다. 이름·이메일·클릭·체류 시간과 모델 피처는 저장하지 않는다. 초기 관심사 입력·저장 API와 UI는 팀 합의 전이므로 제거했다. 기존 가상 독자 피드는 별도의 시연 데이터다.

사용자는 화면의 저장 시작 버튼으로 저장을 선택한다. 저장하지 않아도 가상 피드를 볼 수 있다. 다시 방문하면 쿠키를 통해 이전 독자를 불러온다. 방문 시 만료를 연장하지 않는 고정 30일 방식이다. 저장 기간이 끝난 데이터는 다음 서버 시작 또는 bootstrap 때 정리한다. 정확한 만료 시점부터 API 조회는 거절한다. 물리 삭제는 그 이후 정리 작업 시 수행된다.

## 구조와 선택 이유

화면은 기존 src/app.ts의 가상 독자 흐름을 유지한다. 별도 src/visitor.ts가 프로필 조회와 안내를 담당한다. server/http.ts는 요청과 쿠키 검증을 처리하고 server/visitors.ts는 SQLite 조회·생성·삭제를 담당한다.

JSON 파일 전체를 갱신하는 구조와 SQLite를 비교했다. 동시 요청의 저장 유실을 피하고 서버 재시작 후에도 지속되도록 SQLite를 선택했다. 방문자와 토큰의 관계가 현재 일대일이므로 하나의 visitors 테이블로 구현했다. 여러 기기나 토큰 교체를 지원할 때는 별도 토큰 테이블로 분리해야 한다. 회의 청사진의 논리 설계와 물리 구현의 차이이며 여러 기기 식별은 이번 범위가 아니다.

데이터 형태를 분리하는 Model the Domain 원칙은 쿠키 표식과 내부 독자 ID를 구분하는 선택에 적용했다. 재시도에도 중복 생성하지 않는 Make Operations Idempotent 원칙은 유효한 쿠키의 bootstrap이 같은 독자를 반환하고 초기화 요청을 반복해도 같은 삭제 상태로 끝나는 처리에 적용했다.

## API

모든 변경 요청은 Content-Type: application/json과 설정된 PUBLIC_ORIGIN에 정확히 일치하는 Origin을 요구한다. 독자 ID를 요청 본문에 넣어 다른 사람의 정보를 선택할 수 없다. 응답은 private, no-store다.

| API | 요청 | 결과 |
|---|---|---|
| GET /api/v1/visitors/me | 브라우저 쿠키 | 독자 정보 또는 401. 새 쿠키를 만들지 않음 |
| POST /api/v1/visitors/bootstrap | 빈 JSON 객체 | 최초 201·재방문 200·Set-Cookie와 독자 정보 |
| POST /api/v1/visitors/reset | 빈 JSON 객체 | 현재 독자 행 삭제와 쿠키 만료. 다른 독자에게 영향 없음 |

bootstrap은 새 표식을 발급한 후 다음 me 요청에서 브라우저에 쿠키가 유지되는지도 확인한다. 지원 브라우저의 Web Locks로 동시에 열린 탭의 최초 발급을 조율한다. 다른 탭의 화면은 새로고침 시 최신 상태를 확인한다. Web Locks 미지원 환경이나 쿠키가 외부에서 바뀌는 상황에서 모든 동시성 문제가 해결된 것은 아니다.

## 과거 저장 경로와 실행 (현재 실행 명령 아님)

Node.js 24.19.0 이상이 필요하다. 외부 DB 서버나 npm 패키지는 필요 없다. 기본 경로는 프로젝트의 data/visitors.sqlite다. data 폴더와 SQLite 보조 파일은 Git에서 제외하고 HTTP 정적 파일 허용 목록에서도 차단한다. 데이터가 있는 data 폴더를 삭제하면 서버 정보는 사라진다.

```powershell
npm start
```

기본 주소는 http://127.0.0.1:4173 이다. 기존 서버가 포트를 사용한다면 별도 포트로 실행한다.

```powershell
$env:PORT='4181' # 당시 Node 회귀 서버의 임의 포트. 현재 Compose 기본 포트가 아님
npm ci
npm start
```

VISITOR_DB로 DB 경로를, PUBLIC_ORIGIN으로 브라우저가 접근하는 정확한 출처를 지정할 수 있다. 예를 들어 localhost와 127.0.0.1은 다른 출처이므로 설정한 주소로 접속해야 한다. PUBLIC_ORIGIN에 HTTPS 주소를 지정하면 __Host-news_visitor 쿠키와 Secure를 적용한다. 이 변수만으로 서버가 HTTPS를 제공하지는 않는다. HTTPS 종료 프록시가 필요하며 서버는 로컬 인터페이스에만 바인딩한다. 프록시는 Host·Origin을 임의로 바꾸지 않도록 구성한다.

로컬 HTTP에서는 news_visitor 쿠키와 HttpOnly·SameSite=Lax를 적용한다. Secure 없이 개발용으로 동작하는 설정을 외부 HTTP 배포에 쓰지 않는다. node:sqlite 지원 범위는 [Node 공식 문서](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)를, 쿠키 속성은 [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)를 참고했다.

## 검증

```powershell
npm run check
npm test
npm run build
```

기존 피드 테스트 4개와 새 HTTP 통합 테스트 2개와 기존 DB 전환 테스트 1개를 실행했다. 새 테스트는 실제 요청과 임시 SQLite DB로 신규 발급·독자 분리·프로필 조회·서버 재시작·고정 만료·삭제·조작된 요청·교차 출처 거절·정적 파일 보호·HTTPS 쿠키 헤더를 확인한다. HTTPS 테스트는 설정에 따른 헤더 검증이며 실제 TLS 배포 검증은 아니다.

브라우저에서 관심사 입력이 제거되고 이전 방문자 정보가 조회되는 것을 확인했다. 테스트는 DB에 관심사 열이 없고 API 응답에도 관심사가 없으며 제거한 저장 API가 404인지 확인한다. 쿠키 삭제·만료 시 신규 독자로 바뀌는 처리는 HTTP 테스트로 확인했다.

## 남은 범위

정적 dist 배포만으로는 이 API를 실행할 수 없다. GitHub Pages에서는 방문자 저장이 불가능하며 화면에 서버 연결 안내가 나온다. API 서버와 동일 출처 프록시가 있는 배포 구성이 필요하다.

현재 방문자 식별은 로컬 기능 검증이다. 공개 운영 전에는 개인정보 안내와 정책 검토, 요청 제한, 운영 백업·삭제·보관 자동화, HTTPS와 배포 환경 검증이 필요하다. 쿠키 표식은 로그인 계정이나 사람의 신원을 증명하지 않는다. 쿠키 삭제 후 이력 복원, 다른 기기 연결, 로그인 계정 병합, 클릭·노출·체류 적재, 관심사 기반 피드 정렬과 CTR 학습은 아직 구현하지 않았다.

## 초기 관심사 기능 제거

기존 로컬 DB에 interests 열이 있으면 서버 시작 시 열을 삭제한다. 독자 ID와 토큰 해시는 유지하므로 방문자 연결은 이어진다. 초기 관심사는 사용자 요청으로 제거했으며 선택값을 다른 저장소로 옮기거나 백업하지 않는다.
