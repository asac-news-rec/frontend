# 개인화 뉴스 플랫폼 화면 구성 제안 및 피드백 요청

후속 범위 변경 · 초기 관심사 입력·저장은 미합의이므로 제외했다. 이 문서의 초기 관심사 관련 제안은 확정 명세가 아니며 최신 청사진 v0.4를 우선한다.

작성일 2026-10-29 · 프론트엔드 제안 초안 v0.1

## 문서 목적

화면 설계를 시작하기 전에 프론트엔드에서 생각한 화면 구성과 필요한 정보를 공유합니다. 팀원들의 의견을 받아 구현 범위와 데이터 연결 방향을 맞추고자 합니다.

아래 내용은 확정된 요구사항이 아닙니다. 프로젝트에서 꼭 보여줘야 할 내용이 빠졌는지, 불필요한 기능이 있는지, 백엔드·ML·데이터 측면에서 제공하기 어려운 정보가 있는지 검토 부탁드립니다.

API 경로, 필드 자료형, 이벤트 재시도 같은 구현 규칙은 화면 방향을 정한 뒤 별도로 합의하려고 합니다.

## 1. 화면에서 보여주고 싶은 핵심

프론트엔드에서는 독자별 관심사와 뉴스 이용 이력에 따라 다른 기사가 추천되는 모습을 보여주고자 합니다. 이용 행동이 수집되고 이후 추천에 반영되는 과정도 확인할 수 있으면 좋겠습니다.

우선 다음 시나리오를 제안합니다.

1. 관심사가 다른 가상 독자 중 한 명을 선택합니다.
2. 선택한 독자의 추천 뉴스 피드를 확인합니다.
3. 기사를 선택하고 상세 내용을 읽습니다.
4. 정해진 데이터 처리·추천 갱신 이후 피드를 다시 확인합니다.
5. 다른 독자로 전환해 추천 결과와 추천 이유를 비교합니다.

행동 직후 추천이 즉시 바뀌는지는 아직 정하지 않았습니다. 배치 처리라면 실제 갱신 시점에 맞춰 화면을 표시해야 합니다. 독자별 결과 차이 역시 실제 추천 로직을 연결한 뒤 확인해야 합니다.

**피드백 요청**

- 이 흐름이 팀에서 생각하는 프로젝트 시연 방향과 맞나요?
- 뉴스 이용 경험과 데이터 처리 과정 중 어느 쪽을 화면에서 더 강조하면 좋을까요?

## 2. 화면 구성 제안

| 화면 | 제안하는 내용 | 제안 이유 | 우선순위 |
|---|---|---|---|
| 독자 선택 | 가상 독자 목록, 독자 이름, 초기 관심사, 선택 버튼 | 관심사가 다른 독자를 바꿔가며 개인화 결과를 비교하기 위함입니다. | 우선 구현 |
| 뉴스 피드 | 추천 기사 목록, 카테고리, 추천 이유, 추천 갱신 시각 | 어떤 기사를 왜 추천했는지 확인하기 위함입니다. | 우선 구현 |
| 기사 상세 | 제목, 본문, 카테고리, 발행 시각, 기사 출처 | 실제로 기사를 읽는 흐름을 만들고 읽기 행동을 수집하기 위함입니다. | 우선 구현 |
| 독자 분석 | 최근 읽은 기사, 행동으로 추정한 관심사, 데이터 기준 시각 | 행동과 추천의 관계를 설명하기 위함입니다. | 기본 흐름 완성 후 검토 |

독자 선택은 별도 화면 또는 피드 상단의 선택 메뉴로 구성할 수 있습니다. 초기에는 피드 상단에서 독자를 바꾸는 방식을 제안합니다. 시연 중 화면 이동을 줄이면서 결과를 비교할 수 있기 때문입니다.

**피드백 요청**

- 필수로 추가해야 하거나 제외해도 되는 화면이 있나요?
- 독자 분석 화면은 발표에 필요한가요? 필요하다면 어떤 정보를 보여주면 좋을까요?
- 독자 선택은 시연용 기능으로 두면 될까요? 실제 회원가입·로그인도 필요한가요?

## 3. 뉴스 피드에 표시할 정보

기사 카드는 다음 정보를 중심으로 구성하려고 합니다.

| 표시 정보 | 제안 | 이유 |
|---|---|---|
| 기사 제목 | 필수 | 읽을 기사를 선택하는 기본 정보입니다. |
| 기사 요약 | 제공할 수 있으면 표시 | 본문을 열기 전에 기사 내용을 판단할 수 있습니다. |
| 카테고리 | 표시 | 독자의 관심사와 추천 결과를 비교하기 쉽습니다. |
| 썸네일 | 선택 | 목록을 구분하기 좋지만 이미지 제공 여부에 따라 생략할 수 있습니다. |
| 발행 시각 | 표시 | 기사의 최신성을 확인할 수 있습니다. |
| 추천 이유 | 제공 가능한 근거만 표시 | 개인화가 어떻게 적용됐는지 설명할 수 있습니다. |
| 가상 기사 여부 | 가상 기사에 명시 | 생성한 내용을 실제 보도로 오해하지 않게 합니다. |

추천 이유 문구의 예시는 '처음 선택한 IT 관심사와 관련된 기사입니다'입니다. 실제로 이용 이력을 반영한 경우에만 '최근 읽은 스포츠 기사와 관련된 기사입니다'처럼 표시합니다. 프론트엔드가 이유를 임의로 만들지 않고, 추천 담당자가 제공할 수 있는 근거를 사용하려고 합니다.

카테고리 필터는 후보 기능입니다. 포함한다면 해당 카테고리 안에서 개인화된 기사를 보여주는 방향을 제안합니다. 전체 추천과 카테고리별 추천 중 무엇을 지원할지는 확인이 필요합니다.

**피드백 요청**

- 제목·요약·카테고리·발행 시각·이미지 중 실제 제공 가능한 정보는 무엇인가요?
- 추천 이유를 제공할 수 있나요? 가능하다면 어느 수준의 근거를 줄 수 있나요?
- 카테고리 필터가 초기 구현에 필요한가요?

## 4. 화면 연결에 필요한 데이터

지금 단계에서는 정확한 필드명보다 아래 정보의 제공 가능 여부를 먼저 맞추고 싶습니다.

| 데이터 묶음 | 필요한 정보 | 필요한 이유 |
|---|---|---|
| 독자 | 독자 ID, 표시 이름, 초기 관심사, 이용 이력 유무 | 현재 독자를 구분하고 이력이 없는 경우를 처리합니다. |
| 기사 목록 | 기사 ID, 제목, 요약, 카테고리, 발행 시각, 이미지 여부, 생성·수집 출처 | 피드의 기사 카드를 구성합니다. |
| 기사 상세 | 기사 ID, 본문, 원문·매체 정보가 있다면 해당 출처 | 목록에서 선택한 기사를 정확히 열고 출처를 표시합니다. |
| 추천 결과 | 독자 ID, 추천 묶음 ID, 순서가 있는 기사 목록, 추천 이유, 생성 시각, 데이터 기준 시각, 기본 추천 여부 | 추천 출처를 추적하고 개인화·기본 추천을 구분합니다. |
| 독자 분석 | 최근 읽은 기사, 추정 관심사, 집계 기준 시각 | 분석 화면을 구현하기로 한 경우에 사용합니다. |

초기 관심사는 가상 독자에게 미리 설정한 정보입니다. 추정 관심사는 이용 행동에서 계산한 결과입니다. 화면에서 두 값을 구분해 표시하려고 합니다.

**피드백 요청**

- 각 데이터는 어느 담당자가 만들고 백엔드에서 어떻게 제공할 수 있나요?
- 첫 화면 개발용 샘플 데이터를 먼저 공유할 수 있나요?
- 제공하기 어렵거나 의미가 불분명한 항목이 있나요?

## 5. 행동 데이터 수집에 대한 제안

브라우저에서 발생하는 행동은 아래처럼 구분하려고 합니다. 수집 기준은 데이터·ML 담당자와 합의한 뒤 확정합니다.

| 행동 | 제안하는 의미 | 이유 |
|---|---|---|
| 기사 노출 | 기사 카드가 화면에 일정 비율 이상, 일정 시간 이상 보임 | 데이터를 내려받은 것과 실제로 본 것을 구분합니다. |
| 기사 클릭 | 독자가 피드에서 기사를 선택함 | 어떤 추천 기사에 관심을 보였는지 확인합니다. |
| 읽기 시간 | 기사 상세 화면이 활성화된 시간 | 다른 탭을 보고 있는 시간을 제외하려는 목적입니다. 실제 집중도나 완독을 보장하는 값은 아닙니다. |

행동에는 독자 ID, 기사 ID, 발생 시각을 연결합니다. 추천 피드에서 발생했다면 추천 묶음 ID도 연결하는 방향을 제안합니다. 그래야 어떤 추천이 행동으로 이어졌는지 추적할 수 있습니다.

가상 독자 시뮬레이터가 생성한 행동과 사람이 브라우저에서 발생시킨 행동은 구분해 기록하고자 합니다. 시뮬레이터가 화면을 거쳐야 하는지, 별도로 행동을 생성하는지도 확인이 필요합니다.

**피드백 요청**

- 가상 독자 행동은 별도 시뮬레이터에서 생성하는 것으로 보면 될까요?
- 브라우저에서 직접 발생한 행동도 추천 입력에 포함할까요, 시연 확인용으로만 사용할까요?
- 모델에 필요한 행동은 노출·클릭·읽기 시간으로 충분한가요?

## 6. 이력이 부족하거나 데이터가 없는 경우

| 상황 | 화면 처리 제안 | 이유 |
|---|---|---|
| 신규 독자 | 초기 관심사에 맞춘 기본 피드와 안내 문구 | 이용 이력이 없어도 첫 화면을 사용할 수 있습니다. |
| 초기 관심사도 없음 | 인기 또는 최신 기사로 대체 | 개인화 입력이 없는 상태에서도 기사를 제공할 수 있습니다. |
| 추천 갱신 대기 | 현재 결과와 마지막 갱신 시각 표시 | 행동이 즉시 반영됐다고 오해하지 않게 합니다. |
| 기사 목록 없음 | 해당 조건에 기사가 없다는 안내 | 정상적인 빈 결과와 시스템 오류를 구분합니다. |
| 조회 실패 | 오류 안내와 다시 시도 버튼 | 사용자가 다음 행동을 선택할 수 있습니다. |

**피드백 요청**

- 신규 독자·이력 부족 독자의 기본 추천 방식은 무엇으로 정하면 좋을까요?
- 추천은 어떤 주기로 갱신되나요? 화면에서 갱신 여부를 확인할 수 있나요?

## 7. 우선 구현 범위 제안

첫 단계는 독자를 선택하고 피드에서 기사를 열어보는 흐름으로 잡고자 합니다. 샘플 데이터로 화면을 먼저 검토하고, 이후 실제 API와 행동 수집을 연결합니다. 샘플 화면은 실제 추천 결과와 구분해 표시합니다.

| 단계 | 만들 내용 | 팀에서 확인할 내용 |
|---|---|---|
| 1 | 화면 배치와 샘플 기사 카드 | 필요한 정보가 잘 보이는지, 빠진 기능이 있는지 |
| 2 | 독자 선택·피드·상세 화면 연결 | 화면 이동과 독자 전환 흐름이 맞는지 |
| 3 | 실제 데이터 조회와 행동 전송 연결 | 독자·기사·추천 ID가 올바르게 이어지는지 |
| 4 | 추천 갱신 확인, 필요시 독자 분석 추가 | 실제 데이터 처리 흐름을 설명할 수 있는지 |

이 순서는 핵심 독서 흐름을 먼저 확인하는 Experience First 원칙을 반영한 제안입니다. 팀 일정과 제공 가능한 데이터에 따라 조정합니다.
