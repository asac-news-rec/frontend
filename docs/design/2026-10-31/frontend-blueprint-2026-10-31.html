1 회의에서 제안할 핵심 방향

프론트엔드는 추천 결과를 표시하고 관측 가능한 행동을 기록한다. 백엔드는 독자·기사·추천의 연결을 검증하고 데이터를 저장한다. 데이터 파이프라인은 원본 이벤트를 정제해 피처와 학습 표본을 만든다. ML은 클릭 확률을 예측하고 추천 순서를 제공한다. 프론트엔드가 관심사 점수나 추천 순위를 임의로 계산하지 않는 것을 제안한다.

첫 연결 목표는 독자 선택 → 추천 목록 조회 → 기사 상세 → 행동 저장까지다. 실제 학습 모델이 준비되지 않아도 명시적인 대체 추천과 고정된 API 샘플로 연결 검증을 시작할 수 있다. 행동 저장 성공과 모델 재학습 완료는 서로 다른 상태로 취급한다.

2 현재 상태와 구현 범위

구현 후속 기록 · 2026년 10월 29일. 비로그인 방문자 쿠키 식별만 로컬 Node 서버와 SQLite에 구현했다. 초기 관심사 선택·저장은 팀에서 논의하지 않은 기능이므로 제거했다. 현재 저장하는 데이터는 토큰 해시, 독자 ID, 생성·최근 방문·만료 시각이다. 추천·행동 수집 API는 여전히 제안이며 최신 구현 범위는 ../../implementation/anonymous-visitor-implementation.md를 참고한다.

현재 확인한 프론트엔드는 외부 패키지 설치가 필요 없는 정적 HTML·CSS·JavaScript 프로토타입이다. 가상 독자 3명과 가상 기사 8개를 사용한다. 독자별 미리 정한 순서가 다르며, 이는 학습 모델이 예측한 결과가 아니다.

헤더             서비스 이름 · 시연 데이터 안내

현재 이름과 카테고리는 시연용이다. 카테고리 ID와 표시 문구는 분리하고, 운영 카테고리는 서버 목록을 사용한다. 초기 관심사 입력은 합의된 화면 범위가 아니므로 MVP에서 제외한다. 필요성이 확인되면 별도 안건으로 검토한다. 기존 가상 독자의 사전 설정은 시연용이며 실제 방문자의 입력값이 아니다. 현재 독자 선택 UI를 회원가입이나 실제 인증으로 설명하지 않는다.

목록으로 돌아오면 독자·필터·추천 ID·스크롤 위치를 가능한 범위에서 복원한다. 상세 화면을 보는 동안 새 추천이 도착해도 기존 클릭 출처를 새 추천 ID로 바꾸지 않는다. 화면 갱신은 명시적인 새로고침 또는 다음 피드 진입 시점부터 시작하는 방안을 제안한다.

3.2 MVP와 후속 범위

MVP는 피드·상세·독자 시연·기본 행동 수집·실패 상태다. 검색·북마크·좋아요·댓글·실제 회원가입·독자 분석 대시보드는 후속으로 둔다. 새로운 행동 버튼을 만들기 전, 그 행동을 추천에 어떻게 활용할지 먼저 합의한다.

                                  ↓
독자·과거 행동 → 백엔드 API → 후보 기사 조회 → 과거 피처 → CTR 예측 또는 대체 추천
                     ↓                                      ↓
                 추천 목록 저장 ← 기사 ID·순위·추천 이유·모델 버전
                     ↓
프론트엔드 ← 추천 응답 및 상세 응답
     ↓
노출·클릭·상세 열림·활성 체류 → 이벤트 수집 API → 검증·중복 제거 → 원본 저장
                                                                    ↓
                              다음 추천 ← 피처 갱신·학습·평가 ← 정제·집계

이 그림은 제안한 논리 흐름이다. 저장소 제품, 메시지 큐, 웨어하우스, 모델 서빙 제품의 도입을 확정한 그림이 아니다. 현재는 방문자 조회용 DB와 행동 원본용 Cloud Storage를 구분하고 BigQuery 배치 적재를 우선 추천한다. DB 제품·서비스 분리는 팀과 확정한다. 브라우저가 DB에 직접 접속하거나 DB 자격증명을 보관하지 않는다.

4.1 사용자가 보는 한 번의 흐름

  1. 프론트는 카테고리·시연 독자 목록을 가져온다. 실제 이용자를 도입하면 인증된 서버 주체와 독자 식별자를 연결한다.
  2. 독자 A와 필터를 선택해 추천 생성을 요청한다. 서버는 모델 또는 대체 전략을 선택한다.
  3. 서버는 추천 ID와 기사별 순위를 저장한 뒤 요약을 포함해 반환한다. 카드마다 상세 API를 호출하지 않는다.
  4. 프론트는 받은 순서로 표시하고 실제 가시성 조건을 만족한 카드만 노출로 기록한다.
  5. 링크를 선택하면 클릭을 먼저 큐에 기록하고 상세를 요청한다. 이벤트 전송 때문에 화면 이동을 기다리게 하지 않는다.
  6. 본문 표시가 성공하면 상세 방문 ID를 생성하고 상세 열림을 기록한다. 활성 시간은 증가분으로 전송한다.
  7. 서버는 이벤트 원본의 Cloud Storage 업로드를 확인한 뒤 수락 응답을 준다. 프론트는 수락·중복 이벤트만 큐에서 제거한다.
  8. 정제·집계·모델 갱신 이후 새로운 추천 요청에서 변경된 결과를 제공한다. 갱신 주기는 팀이 정한다.

5 화면과 API 데이터 계약

공통 제안은 JSON snake_case, 문자열 ID, UTC ISO 8601 시각, 밀리초 단위 시간 길이다. 화면에는 한국 시간으로 표시한다. null은 미측정·해당 없음이며 숫자 0과 구분한다. 계약의 버전은 API 경로와 이벤트 schema_version으로 관리한다.

사용자 동작제안 API응답과 프론트 처리
비로그인 방문 시작POST /api/v1/visitors/bootstrap신규 제안·쿠키 확인 또는 발급·서버 독자 컨텍스트 반환·7.6절 참고
시작GET /api/v1/categories 및 GET /api/v1/readers선택 목록 표시·시연 독자 조회 권한 별도 확인

가상 독자 시연의 추천 요청은 reader_id, category_id, limit를 보낸다. 일반 방문자는 7.6절의 쿠키 기반 서버 독자 확인을 적용하고, 본문 reader_id로 다른 독자를 선택할 수 없도록 한다. 요청별 Idempotency-Key를 만들고 동일 요청의 재시도에만 재사용한다. 초기 limit=20, 상한 50, 키 유효기간 24시간은 기존 초안의 제안값이며 확정이 필요하다.

독자 A 조회 직후 B로 전환했을 때 A 응답이 늦게 도착해도 B 화면을 덮지 않아야 한다. 기존 화면 코드에는 요청 순서 확인이 있으며 실제 API 연결 시 취소 또는 요청 세대 확인을 유지한다. 이벤트도 발생 순간의 독자와 추천을 고정한다.

6 수집할 사용자 행동과 측정 정의

6.1 우선 수집할 네 가지

50%·1초, 10초 체류 보고는 검증 전 초기값이다. 작은 화면에서 큰 카드가 50% 이상 보일 수 없는 경우를 확인하고 카드 크기 또는 관찰 영역을 조정한다. Intersection Observer는 화면과 요소의 교차를 관찰하는 수단이며 다른 창에 가려지는 상황까지 완벽하게 판정한다고 가정하지 않는다. [S3]

노출은 session_id·recommendation_id·article_id 조합별 1회로 시작한다. 추천 항목은 한 목록 안에서 중복되지 않도록 한다. 재노출 횟수를 연구하려면 이 중복 규칙과 CTR 분모를 함께 변경해야 한다. 세션은 탭별로 만들고 독자 전환 또는 마지막 활동 이후 30분이 지나면 새 ID를 부여하는 방안을 제안한다.

6.2 빠른 클릭과 직접 진입

노출 1초가 되기 전에 클릭할 수 있다. 이때 클릭은 그대로 저장하고 exposure_id=null과 연결된 추천·기사·순위를 남긴다. 조건을 만족하지 않은 article_impression을 가짜로 생성하지 않는다. 상세를 직접 열면 추천 ID와 클릭 ID가 null일 수 있으며 피드 클릭을 만들지 않는다.

키보드 Enter, 보조 버튼, 새 탭 열기도 수집 대상으로 검토한다. 한 동작을 여러 DOM 핸들러에서 이중 기록하지 않도록 interaction_id를 사용한다. 새 탭 상세에 출처를 넘기는 방식은 라우트 또는 제한된 전달 토큰으로 설계하고 원래 추천 출처를 검증한다.

6.3 체류와 전송 실패

활성 시간 10초마다 증가분을 전송하고 탭 숨김·포커스 상실·독자 전환·상세 이탈 때 남은 증가분을 기록한다. 10초·10초·3초를 수락하면 23,000ms다. 브라우저 지연이 발생해도 숨겨진 시간 전체를 읽은 시간으로 계산하지 않는다. 비활성 사용자 판별을 위한 유휴 기준은 후속 실험으로 정한다.

평상시에는 소량 배치와 주기적 flush를 사용한다. 초기 제안은 최대 20건 또는 5초, 큐 상한 500건이며 부하 확인 후 결정한다. 종료 직전 sendBeacon은 보조 수단이다. true 반환은 큐에 들어갔다는 뜻이며 서버 적재 성공을 보장하지 않는다. 다음 실행에서 미확인 이벤트를 같은 ID로 재전송하고 서버에서 중복 제거한다. [S4]

큐는 인증된 사용자 범위로 격리한다. 로그아웃·삭제 요청·독자 전환 때 다른 독자의 이벤트로 바꾸지 않는다. 큐 만료·용량 초과 시 폐기 건수는 별도 품질 로그로 남긴다. 수집 동의·보관 기간·삭제 범위는 실제 이용자 도입 전에 팀이 정책으로 확정한다.

6.4 후속 행동

스크롤 최대 도달률은 0~1로 추가할 수 있으나 완독 여부와 같지 않다. 카테고리 변경은 명시적인 탐색 신호이며 모든 기사 이벤트에 article_id를 강제하지 않도록 별도 이벤트 스키마를 정의한다. 북마크·좋아요·관심 없음은 해당 UI가 생긴 뒤 추가한다. 마우스 이동 전체·키 입력 전체·이름·이메일·정밀 위치는 초기 추천 연구 범위에서 수집하지 않는 것을 제안한다.

6.5 이벤트 로그를 저장하는 전체 흐름

현재 실시간 추천 반영을 목표로 하지 않는다는 전제에서 ‘프론트엔드 → 행동 수집 API → Cloud Storage 원본 저장 → BigQuery 배치 적재’를 우선 추천한다. 팀 회의에서 검토할 권장안이며 인프라 구축을 확정하거나 완료한 것은 아니다. Pub/Sub는 초기 필수 구성에서 제외한다. 방문자 표식 조회는 별도 영속 DB를 사용한다. 이벤트 수집·저장은 아직 구현하지 않았으며, 현재 구현된 쿠키 방문자 식별과 구분한다.

브라우저의 행동 발생

같은 출처 POST /api/v1/events/batch
  ↓ 쿠키 표식으로 서버 독자 확인

행동 로그는 클릭·노출·읽기 상태를 분석하기 위한 데이터다. 서버 오류와 응답 시간을 확인하는 운영 로그와 구분한다. 운영 로그는 Cloud Logging으로 관리하고, 행동 원본은 위 저장 경로에서 스키마와 재전송 규칙을 관리하는 방안을 제안한다. 동작 확인을 위해 Cloud Logging에 쿠키 원문이나 이벤트 전체를 무조건 출력하지 않는다.

6.6 Cloud Storage와 BigQuery 배치를 추천하는 이유

현재 조건 또는 요구권장안이 맞는 이유감수할 부담
실시간 추천 반영은 초기 목표가 아님적재·정제·피처 생성을 일정 주기로 실행할 수 있음최신 행동이 추천에 반영되기까지 지연
수집 규칙과 피처 설계가 바뀔 수 있음원본 파일을 보관하면 새 규칙으로 재처리 가능파일 보관·삭제·버전 관리 필요
데이터 흐름을 팀별로 연결해야 함프론트 수집·백엔드 검증·데이터 정제·ML 학습의 입출력이 명확함파일 스키마와 전달 계약 합의 필요
Pub/Sub 없이 시작하고자 함Cloud Storage 파일을 BigQuery로 배치 적재할 수 있음적재 작업·재시도·완료 상태를 직접 관리
학습 입력까지의 추적이 중요함파일·작업 ID·event_id로 원본에서 표본까지 연결 가능중복·충돌·지연 데이터 처리 필요

이는 요구사항에 따른 설계 판단이며 다른 구성보다 비용이나 성능이 우수하다고 측정한 결론은 아니다. 먼저 소량의 실제 이벤트로 끝까지 검증한다. Cloud Storage 업로드 완료는 수집 완료, BigQuery 적재·정제 완료는 분석 준비 완료로 구분한다. [S10]

Bronze·Silver·Gold는 서비스 이름이 아니라 가공 단계다. Bronze는 수집 API의 기본 검증과 서버 시각 부여를 거친 원본에 가까운 이벤트 파일, Silver는 중복·충돌·오류를 처리한 데이터, Gold는 독자별 집계·CTR 표본·모델 피처다. 모든 단계를 별도 제품으로 만들 필요는 없다. Silver와 Gold는 BigQuery 테이블로 시작할 수 있다.

방문자 DB는 쿠키 토큰 해시와 독자 ID의 빠른 연결 조회를 맡고, Cloud Storage는 행동 원본 보관을 맡는다. 방문자 DB에 전체 행동을 반드시 중복 저장할 필요는 없다. BigQuery도 방문자 인증 조회용 DB로 사용하지 않는다.

6.6.1 로그 수집 서버와 대안 비교

‘별도의 로깅 서버’는 행동 수집을 담당하는 API 서비스다. 별도 VM이나 메시지 브로커가 반드시 필요하다는 뜻은 아니다. 초기에는 기존 백엔드 안의 전용 모듈·엔드포인트로 두거나, 독립 배포가 필요하면 Cloud Run 서비스로 분리할 수 있다. 서비스 분리 여부는 담당자와 트래픽 요구에 따라 결정한다.

Cloud Storage 배치 경로를 우선 제안하고 DB 우선 저장·BigQuery 직접 기록은 요구가 달라질 때 비교할 대안으로 둔다. 실시간 반영이나 유입 급증에 따른 장애 분리가 필요해지면 Pub/Sub를 재검토한다. 상세 대안 비교는 ../../research/gcp-behavior-logging-research.md를 참고한다. [S9][S10][S11]

6.7 저장 데이터와 성공 응답 기준

데이터 묶음저장할 값과 규칙
이벤트 식별event_id, schema_version, event_type. 한 행동의 재시도는 같은 ID·같은 본문
독자와 세션쿠키로 서버가 결정한 reader_id, 프론트가 만든 session_id. 토큰 자체는 저장 금지
기사와 추천 출처article_id, recommendation_id nullable, rank 및 exposure_id 등. 서버의 추천 항목과 대조
시간클라이언트 occurred_at과 서버 received_at을 분리. UTC 시각·체류는 밀리초
출처browser / simulator / test 등 인증된 발신 경로와 독자 종류 구분
종류별 속성노출 비율·지속 시간, 클릭 interaction_id, 상세 article_view_id, 체류 sequence·증가분

일반 방문자의 reader_id는 요청 본문만으로 결정하지 않는다. 기존 JSON의 reader_id는 설명용 시연·내부 저장 예시다. 쿠키와 본문 ID가 충돌하거나 추천 소유자가 다르면 거절한다. 정의되지 않은 이벤트 종류·속성, 잘못된 시간 단위·크기, 과도한 배치는 수집 경계에서 거절한다. 실제 사용자 IP·쿠키 원문·서비스 계정 키를 학습 이벤트에 넣지 않는다.

accepted는 ‘유효 이벤트가 들어 있는 원본 파일의 Cloud Storage 업로드 성공을 확인했다’는 뜻으로 정의한다. 메모리나 Cloud Run 로컬 디스크에만 넣고 수락하지 않는다. 요청 배치별 batch_id를 발급하고 재시도에는 같은 batch_id와 같은 이벤트 본문을 사용한다. 배치 전송 단위는 프론트 20건 또는 5초 등 기존 제안과 함께 검증 후 확정한다.

서버는 독자 범위와 batch_id에서 결정한 고정 객체 이름으로 조건부 생성을 사용한다. 기존 객체가 있으면 비교용 요청 해시로 동일 요청인지 검사하고, 같으면 duplicate, 다르면 BATCH_ID_CONFLICT로 거절한다. 해시는 최초 수신 시각처럼 재시도 때 달라지는 서버 메타데이터를 제외한 정규화된 요청에 대해 계산한다. 기존 객체를 비교할 권한 또는 별도 멱등 기록 저장소가 필요하며, 객체 존재만 보고 재시도를 성공 처리하지 않는다. Cloud Storage의 ifGenerationMatch=0 같은 생성 전제조건을 후보로 사용한다. [S12]

파일 경로는 예를 들어 bronze/events/received_date=2026-10-29/reader_bucket=ab/batch-UUID.jsonl 형태로 설계할 수 있다. 객체 이름에는 쿠키 토큰을 넣지 않는다. 날짜를 경로에 쓰면 재시도 시 날짜가 달라져도 같은 객체를 찾도록 최초 확정한 경로 또는 서버 멱등 매핑을 유지해야 한다. 저장된 파일은 덧붙여 수정하지 않고 새 객체로 보관한다.

API 배치는 이벤트별 결과를 반환한다. 검증에서 탈락한 항목은 rejected, 업로드에 포함한 항목은 업로드 확인 후 accepted다. 유효한 항목들의 파일 저장에 실패하면 그 항목들을 재시도 대상으로 반환한다. 응답 유실 시에도 배치 내용과 ID를 유지해 재전송한다. 첫 버전에서는 부분 수락 배치 재시도 시 이미 거절된 항목을 제외해 새 본문을 만드는 대신 원래 요청을 유지하도록 계약을 단순화한다.

서로 다른 batch_id로 같은 event_id가 들어오면 Bronze에는 중복이 남을 수 있다. 따라서 수집 단계의 duplicate는 동일 배치 재시도 확인이며 이벤트 전체의 중복 제거 완료를 의미하지 않는다. Silver에서는 event_id와 정규화된 이벤트 본문을 비교해 동일 행동을 한 번만 계산한다. 같은 ID·다른 본문은 EVENT_ID_CONFLICT로 격리하고 학습에서 제외한다. received_at은 본문 동일성 비교에서 제외하며 원본에는 첫 수신·재수신 근거를 보존한다.

6.8 BigQuery 배치 적재와 운영

Cloud Storage에서 BigQuery로 자동 전송된다고 가정하지 않는다. 배치 작업이 미처리 객체 목록을 확정하고 BigQuery load job을 실행한다. 객체 이름·generation·적재 작업 ID·처리 상태를 기록한 manifest를 관리하고 적재 성공을 확인한 뒤 상태를 갱신한다. 재실행 시 같은 파일이 중복 반영되지 않게 작업 ID와 정제 규칙을 유지한다. 늦게 업로드된 파일은 이전 날짜 경로라도 미처리 객체이면 다음 작업에서 발견해야 한다.

처음에는 수동 실행으로 검증하고, 후속으로 Cloud Scheduler와 Cloud Run Job 등 주기 실행 구성을 검토한다. 시간 단위·일 단위 등 적재 주기, JSONL 형식·압축 여부·파일 크기, manifest 저장 위치는 데이터팀과 확정한다. 요청마다 작은 파일이 생기면 적재 시 여러 파일을 묶거나 별도 파일 통합 단계를 검토한다. 파일마다 load job을 남발하지 않으며 데이터량을 측정해 조정한다. 이 구조가 언제나 저렴하다고 가정하지 않는다. [S10]

수집 API 거절·업로드 실패, 브라우저 큐 폐기, 원본 파일·이벤트 수, 미처리 파일 나이, 적재 성공·실패·충돌 건수를 감시한다. 삭제 기능을 확장하면 방문자 DB뿐 아니라 Cloud Storage 원본·BigQuery·집계의 삭제 범위도 정한다. 원본 보관 30일은 논의안이며 실제 보관 정책·만료 설정은 미정이다.

현재 방문자 SQLite는 로컬 검증용이다. Cloud Run의 기본 파일시스템은 인스턴스 종료 뒤 유지되지 않으므로 파일을 여기에 모아둔 채 수집 완료로 처리하지 않는다. 배포 시 PORT와 0.0.0.0 바인딩, HTTPS·동일 출처 라우팅, 방문자 영속 DB 전환이 필요하다. 서비스 계정 키는 브라우저에 넣지 않고 서버의 권한을 수집용과 분석용으로 나눈다. [S11]

7.3 정합성과 보관

서버는 수집 경계에서 이벤트 종류별 필드·형식·권한을 검증한다. 독자 A의 추천을 독자 B가 자신의 이벤트로 보낼 수 없게 한다. 추천 항목과 rank를 서버의 저장 목록에 대조하고, 동일 event_id의 본문 충돌은 Silver에서 격리한다. 체류는 event_id 외에 article_view_id+sequence의 중복도 Silver에서 제거한다. 수집 API의 즉시 중복·충돌 판정 범위는 6.7절의 동일 배치 재시도다.

추천 이력·원본 이벤트·중복 키의 초기 보관 기간은 30일을 논의안으로 둔다. 이는 법적 기준이 아니라 프로젝트 운영 제안이다. 추천 이력이 이벤트보다 먼저 삭제되면 추적이 끊기므로 연결 보관 기간을 함께 정한다. 중복 키를 지운 뒤 오래된 큐 이벤트가 재전송되는 경우에는 수락 가능 기간을 검사한다. 삭제 기능을 도입할 때 원본·집계·학습 표본까지 추적하는 범위를 결정한다.

7.4 로그인 없이 재방문자를 알아보는 방법

로그인하지 않은 방문자도 이전 행동에 연결할 수 있다. 제안 방식은 브라우저 쿠키에 임의의 방문자 식별 토큰을 저장하고, 서버 DB에서 그 토큰을 독자 ID와 연결하는 것이다. 다음 방문 때 브라우저가 같은 토큰을 보내면 서버가 이전 독자 기록을 찾는다. 쿠키의 저장·전송은 브라우저가 처리한다. [S5]

다만 확인하는 것은 ‘같은 사람’이라는 신원이 아니라 ‘같은 쿠키를 가진 브라우저 프로필’이다. 한 사람이 휴대폰과 PC를 쓰면 서로 다른 익명 독자가 되고, 여러 사람이 같은 브라우저 프로필을 공유하면 행동이 섞일 수 있다. 사용자에게는 ‘이 브라우저의 방문자 정보’라는 표현이 더 정확하다.

멘토가 말한 ‘쿠키에 데이터를 저장해서 보내는 방식’에는 두 가지가 있다. 하나는 관심사나 클릭 목록을 쿠키 값에 직접 넣는 방식이고, 다른 하나는 조회용 표식만 쿠키에 넣고 서버에서 데이터를 찾는 방식이다. 우리 프로젝트에는 두 번째를 제안한다. 서버 DB에 행동을 쌓아 학습하고, 여러 이벤트를 추천 결과까지 연결하기가 쉽기 때문이다.

브라우저의 쿠키                서버의 방문자 연결표           서버의 행동 DB
임의 토큰 K7...        →       K7...의 해시 → reader_042  →  클릭·노출·체류 기록

오늘 방문     토큰 없음 → 서버가 토큰 발급 → 브라우저가 저장
내일 방문     같은 토큰 자동 전송 → reader_042 조회 → 기존 독자와 연결

여기서 토큰은 실제 운영 값이 아닌 설명용이다. ‘번호표는 브라우저에, 번호표에 해당하는 이용 기록은 서버에’ 두는 구조다. 이름이나 이메일을 몰라도 같은 브라우저의 이전 행동에 연결할 수 있다.

7.6 첫 방문부터 재방문까지의 요청 흐름

다음 API는 신규 제안이며 현재 구현되어 있지 않다. 일반 방문자 경로와 가상 독자 시연 경로를 구분한다.

  1. 화면 시작 시 POST /api/v1/visitors/bootstrap을 호출한다. 익명 개인화 수집을 허용한 상태에서만 지속 식별자를 발급하는 정책을 초기 제안으로 둔다. 동의가 필요한 범위와 안내는 실제 이용자 도입 전에 별도 검토한다.
  2. 서버는 쿠키가 없으면 안전한 난수 토큰과 anonymous 독자 레코드를 생성한다. visitor_tokens에 토큰의 해시와 reader_id를 저장하고 응답의 Set-Cookie로 원문 토큰을 전달한다.
  3. 응답 본문에는 화면에 필요한 reader_id, reader_type, 생성·최근 방문·만료 시각만 반환한다. 초기 관심사는 요청하거나 저장하지 않는다. Set-Cookie로 설정한 HttpOnly 토큰을 화면 JavaScript가 읽어 처리할 필요는 없다.
  4. 추천·기사·이벤트 API 호출 때 브라우저가 범위에 맞는 쿠키를 보낸다. 서버는 유효한 토큰으로 독자를 확인하고 그 독자의 과거 이력을 조회한다.
  5. 다음 날 같은 브라우저에서 bootstrap을 호출하면 같은 독자 ID를 반환한다. 새로운 session_id를 만들되 과거 events는 같은 reader_id 아래에 남긴다.
  6. 토큰이 만료·폐기되었거나 알 수 없는 값이면 새로운 방문자로 처리한다. 알 수 없는 클라이언트 토큰을 그대로 서버의 새 독자 키로 채택하지 않는다.

HTTPS와 동일 출처 API를 가정한 헤더 예시는 다음과 같다. 실제 토큰은 아래 문자열보다 충분히 길고 예측 불가능하게 생성한다.

첫 방문 서버 응답
Set-Cookie: __Host-news_visitor=<random-token>; Path=/; Max-Age=2592000; Secure; HttpOnly; SameSite=Lax

다음 API 요청에서 브라우저가 붙이는 헤더
Cookie: __Host-news_visitor=<random-token>

30일은 논의용 쿠키 유효기간이며 영구 식별 보장이 아니다. Secure는 HTTPS 전송, HttpOnly는 화면 스크립트의 직접 접근 제한, SameSite=Lax는 교차 사이트 요청에서의 전송 제한에 관계된다. __Host- 접두사 조건에 맞게 Domain을 설정하지 않고 Path=/와 Secure를 사용한다. 이 설정은 전체 보안 검증을 대신하지 않는다. [S5][S6]

일반 방문자의 추천·이벤트 API는 본문 reader_id를 독자 선택 권한으로 취급하지 않는다. 가능하면 요청에서 생략하고 쿠키로 서버가 결정한다. 기존 시연 계약 호환 때문에 포함한다면 쿠키의 독자와 일치하는지 검사한다. 이 문서의 reader_id를 가진 JSON은 가상 독자 시연 또는 내부 저장 형식의 예시로 해석하고, 공개 API 명세에서는 두 경로를 분리한다.

익명 토큰 소유는 계정 로그인이나 실명 인증을 뜻하지 않는다. 내 기록 조회·초기화 등 익명 기능의 범위도 좁게 설계하고, 상태를 변경하는 API에는 Origin 확인 등 CSRF 대책을 적용한다. 토큰만 알면 다른 사람의 민감한 계정 데이터에 접근하는 구조를 만들지 않는다. 식별 응답과 개인화 피드는 공유 캐시에 섞이지 않게 Cache-Control: private, no-store 등 응답 정책을 검토한다.

7.7 프론트와 백엔드 배포 주소가 중요한 이유

프론트와 API를 같은 출처로 제공하는 구성을 우선 제안한다. 예를 들어 https://news.example.com 화면이 같은 주소의 /api/v1/...를 호출하도록 리버스 프록시를 둔다. 이 주소는 설명용이다. 동일 출처 fetch는 기본적으로 쿠키를 포함할 수 있어 연결이 단순하다. [S7]

프론트가 GitHub Pages의 github.io 주소이고 API가 전혀 다른 사이트라면 교차 사이트 쿠키 문제가 생긴다. credentials: include, 정확한 허용 Origin과 자격증명 CORS 설정이 필요하며 SameSite=Lax 쿠키는 교차 사이트 fetch로 보내지지 않는다. SameSite=None; Secure를 설정해도 브라우저의 제3자 쿠키 제한을 해결한다고 보장할 수 없다. 쿠키 설정 하나로 해결하려 하기보다 같은 출처 /api 프록시 또는 배포 도메인 구성을 팀에서 정한다. 정적 GitHub Pages 자체가 백엔드 역할을 하거나 서버 방문자 쿠키를 발급하는 것은 아니다. [S5][S7][S8]

localStorage에 방문자 ID를 저장해서 API 본문으로 보내는 방법도 간단한 시연에는 가능하다. 하지만 화면 스크립트가 값을 읽고 바꿀 수 있어 서버 인증 근거로 그대로 믿을 수 없다. 쿠키도 요청을 보내는 자의 실명을 증명하지는 않는다. 우리 제안은 서버 발급 토큰·서버 연결표·요청 검증을 결합하는 방식이며, 브라우저 지문이나 IP로 쿠키 삭제를 우회해 다시 연결하는 방법은 사용하지 않는다.

UI에는 ‘이 브라우저의 추천 기록 초기화’를 후속 기본 기능으로 제안한다. 단순 쿠키 삭제는 브라우저와 서버의 연결만 끊으며 서버의 과거 이벤트까지 자동 삭제하지 않는다. 기록 삭제를 제공한다면 쿠키를 지우기 전에 현재 토큰으로 삭제·집계 무효화 작업을 요청하고 처리 범위를 안내해야 한다. 쿠키가 이미 사라지면 해당 익명 기록의 소유를 다시 증명하기 어렵다는 한계도 명시한다.

지속 식별을 거부하거나 저장소를 사용할 수 없는 방문자는 기본 피드를 계속 볼 수 있게 한다. 재방문 개인화가 이어지지 않는다는 점을 설명하고 브라우저 지문으로 대체하지 않는다. 로그인 기능을 추가하더라도 과거 익명 이력을 계정에 무조건 합치지 않으며, 연결 동작·동의·공용 브라우저·로그아웃 후 토큰 교체를 별도로 정한다.

8 CTR 모델 피처와 라벨 설계

CTR은 정의한 노출 중 클릭으로 이어진 비율이다. pCTR은 독자·기사·상황이 주어졌을 때 클릭할 확률의 예측값이다. ‘상단 카드라서 많이 눌렸다’는 위치 효과와 ‘관심이 있어서 눌렀다’는 효과가 섞일 수 있으므로 노출 순위를 보관해야 한다.

MIND는 제시한 기사와 클릭·미클릭, 이전 클릭 이력을 함께 제공한다. EB-NeRD는 기사 정보, 노출 로그, 이전 클릭 이력과 읽기·스크롤 관련 정보를 제공한다. 이를 참고하되 두 데이터셋의 노출 정의가 우리 브라우저의 50%·1초 측정 규칙과 동일하다고 가정하지 않는다. [S1][S2]

8.1 학습 표본과 CTR 분모

초기 모델은 ‘서버가 제공한 추천 항목 중 관측 기간 내 클릭 여부’를 예측하는 served-item CTR로 시작하는 방안을 제안한다. 한 표본은 recommendation_id+article_id 조합이다. 서버는 실제 페이지 응답에 포함한 항목의 served_at을 기록하고 아직 내려주지 않은 다음 페이지 후보는 분모에서 제외한다. 응답 기록은 브라우저 수신을 보장하지 않으므로 통신 실패에 따른 오차는 남는다. 실제 화면 노출이 확인된 항목만 대상으로 계산한 viewable CTR은 별도 지표로 보고한다. 둘의 이름과 분모를 섞지 않는다.

구분분모 또는 대상장점과 한계
제공 기준 CTR제공된 고유 추천 항목빠른 클릭을 포함·아래쪽 미열람 항목도 미클릭에 포함됨
가시 노출 기준 CTR조건을 만족한 고유 노출관측 가능한 선택 기회에 가까움·빠른 클릭이 제외될 수 있음

초기 클릭 관측 기간은 항목별 최초 served_at 이후 30분을 제안한다. 같은 추천·기사의 클릭이 여러 번 있어도 라벨은 1이다. 관측 기간이 끝나고 지연 수신 유예 기간까지 지난 항목만 미클릭 0으로 확정한다. 유예 기간은 수집 지연을 측정한 뒤 정한다. 창을 벗어난 클릭은 원본에 남기되 이 라벨에는 포함하지 않는다. 빠른 클릭은 제공 기준 표본에는 포함되고, 가시 노출 기준에서는 별도로 분리 보고한다.

8.3 누출 방지와 평가

현재 클릭의 결과, 현재 상세 체류, 현재 스크롤은 해당 클릭의 사전 예측 피처로 사용하면 안 된다. 이후 추천에서의 과거 이력으로는 사용할 수 있다. 추천 시각이 t라면 occurred_at < t이고 received_at <= t인 관측만 후보로 삼고 feature_as_of <= t를 보장한다. 당시 사용한 피처 버전 또는 재현 가능한 스냅샷을 저장한다.

시간순으로 학습·검증·테스트를 나눈다. 테스트 기간 클릭을 이전 관심사 집계에 포함하지 않는다. 가상 시뮬레이터, 사람이 조작한 가상 독자, 실제 이용자 데이터는 데이터셋 구분자로 분리하고 결과를 따로 보고한다. 시뮬레이터의 행동 규칙을 모델이 맞혔다고 실제 독자의 추천 품질을 입증한 것으로 해석하지 않는다.

처음에는 최신순·인기순을 기준선으로 두고 간단한 로지스틱 회귀 같은 모델부터 비교하는 방안을 제안한다. AUC와 Log loss는 클릭 분류·확률 품질을, NDCG@K는 목록 내 순위 품질을 살핀다. 단일 클래스나 양성 없는 묶음의 지표 처리 규칙을 명시한다. 실제 온라인 CTR 향상은 별도 비교 실험 전에는 주장하지 않는다.

모델 실패가능한 대체 전략으로 응답·모두 실패하면 503대체 추천 또는 재시도 안내

유효 클릭 0개=new, 1~4개=insufficient, 5개 이상=sufficient는 기존 초안의 임시 구분이다. 클릭 5개가 모델 준비나 품질을 보장하지 않으며 ML 담당자가 최소 데이터와 평가 결과로 수정한다. 배치 주기·캐시 유효시간·독자에게 결과가 바뀌는 시점은 미정이다. 생성 시각과 피처 기준 시각을 응답해 갱신 지연을 설명한다.

  1. API 샘플과 이벤트 스키마 합의. 정상·신규·빈 결과·오류의 고정 입력으로 프론트 검증.

11.3 프론트 담당자의 발표 문장

“현재 화면은 가상 데이터로 만든 검토용 초안입니다. 저는 추천 목록과 상세를 API로 연결하고, 실제 화면 노출·클릭·상세 열림·활성 체류를 기록하는 부분을 맡는 방향을 제안합니다. 추천 결과를 표시하는 데 필요한 필드와 학습에 필요한 행동 ID를 오늘 맞추고 싶습니다. 특히 CTR에서 내려준 기사를 분모로 볼지 실제 보인 기사만 볼지, 클릭 관측 기간을 어떻게 둘지 합의가 필요합니다. 계약이 정해지면 모델이 완성되기 전에도 샘플 응답으로 화면과 이벤트 저장을 단계적으로 검증할 수 있습니다.”

멘토에게는 노출 기준과 라벨의 적절성, 가상 데이터 평가의 한계, 초기 모델에 꼭 필요한 피처, 현 규모에 맞는 저장 구조를 질문한다. 답변은 결정표에 남기고 API·이벤트 계약 버전과 담당자를 갱신한다.
