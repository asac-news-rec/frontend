정리 범위

멘토의 “원본 데이터를 5분씩 저장했다면 어느 주기로 가공할 것인가?”라는 질문 이후, 이 채팅에서 논의한 내용을 정리한다. 회의 전체의 추가 전사 내용을 요약한 문서는 아니다. 아래의 건수·시간·후보 개수는 별도로 명시하지 않는 한 설명용 예시이며, 구현 완료를 의미하지 않는다.

1. 전체 구조

기사 DB에는 기사 자체를 저장하고, 추천 반환 기록과 사용자 행동은 로그로 보존한다. 로그를 연결해 학습 데이터를 만들고, 학습된 하나의 모델로 사용자별 후보 기사에 점수를 계산한다.

기사 생성 → 기사 DB
                  ↓ 기사 조회
프론트 → 웹 Backend → 추천 API
           ↓ 최종 목록·식별자 응답
         프론트

웹 Backend의 추천 반환 기록 ─┐
                            ├→ 로깅 서버 → GCS 원본 로그
프론트의 노출·클릭·체류 기록 ─┘                 ↓
                                      Airflow 작업 조율
                                               ↓
                                BigQuery 적재·결합·피처 생성
                                               ↓
                                         모델 학습
                                               ↓
                                    추천 API에 모델 반영

2. 로깅 서버와 원본 저장

기사 테이블에 조회마다 생기는 request_id와 impression_id를 추가하지 않는다. 별도 운영 DB를 새로 만들 필요 없이 다음처럼 나눌 수 있다.

저장 위치 내용
기사 DB 기사 ID, 제목, 본문, 분류, 발행 시각 등
GCS served 로그 request_id, impression_id, 사용자, 기사, 순서, 반환 시각
GCS actions 로그 event_id, impression_id, 행동 종류, 발생 시각, 시간 값 등
BigQuery 원본 로그 테이블과 정제·학습용 테이블

로깅 서버가 수신 → 임시 보관 → 파티션별 JSONL 생성 → GCS 업로드를 담당한다. 클라이언트는 클릭 등의 이벤트를 JSON으로 전송한다.

클라이언트
  │ POST /events : 클릭 JSON 한 건
  ▼
로깅 서버
  ├─ 이벤트 검증
  ├─ event_time으로 5분 파티션 결정
  ├─ 파티션별로 이벤트 보관
  └─ 1,000건 또는 30초마다 JSONL 생성 → GCS 업로드

저장 기준과 처리 주기

구분 예시 의미
파티션 단위 5분 이벤트를 어느 저장 경로에 넣을지 결정
파일 생성 기준 1,000건 또는 30초 이벤트를 얼마나 모아서 파일 하나로 저장할지 결정
가공 배치 주기 1시간 얼마만큼의 원본을 모아 집계할지 결정

세 기준은 독립적이다. 5분 파티션은 5분 동안 기다렸다가 저장하라는 뜻이 아니다. 같은 파티션 안에서도 파일 생성 기준에 따라 여러 JSONL 파일이 만들어진다. 숫자는 설명용 예시다.

코드 구성

아래 파일명은 구성 예시다. 프로젝트에서 로깅 서버를 담당하는 서비스에 구현한다.

logging_service/
  api.py          ← JSON 요청 수신
  event_buffer.py ← 이벤트를 모으고 저장 시점 결정
  storage.py      ← 파티션 경로·JSONL 생성·GCS 업로드

storage.py: 파티션 경로와 JSONL 생성

다음 코드는 JSONL 내용과 저장 경로를 만드는 예제다. HTTP 서버, 버퍼의 주기 실행, 실제 GCS 업로드는 포함하지 않는다.

import json
from collections import defaultdict
from datetime import datetime
from uuid import uuid4
from zoneinfo import ZoneInfo

KST = ZoneInfo("Asia/Seoul")


def get_partition(event):
    # event_time에는 +09:00 등 시간대가 포함되어야 한다.
    event_time = datetime.fromisoformat(event["event_time"])
    if event_time.tzinfo is None:
        raise ValueError("event_time에 시간대가 필요합니다.")

    event_time = event_time.astimezone(KST)

    # 09:02 → minute=00, 09:07 → minute=05
    minute = (event_time.minute // 5) * 5

    return (
        f"events/date={event_time:%Y-%m-%d}/"
        f"hour={event_time:%H}/minute={minute:02d}"
    )


def make_jsonl_files(events):
    grouped = defaultdict(list)

    # 같은 파티션에 해당하는 이벤트끼리 분류한다.
    for event in events:
        partition = get_partition(event)
        grouped[partition].append(event)

    files = []

    for partition, partition_events in grouped.items():
        object_name = f"{partition}/part-{uuid4().hex}.jsonl"

        # JSON 한 건을 한 줄로 직렬화한다.
        content = "".join(
            json.dumps(event, ensure_ascii=False) + "\n"
            for event in partition_events
        )

        files.append((object_name, content))

    return files

입력과 저장 결과 예시

서버에 모인 이벤트 세 건을 위 함수에 전달한다.

for object_name, content in make_jsonl_files(events):
    print(object_name)
    print(content)
    # 이 위치에서 content를 GCS의 object_name 경로로 업로드한다.

이벤트 시각을 기준으로 파일 두 개가 만들어진다. 고유ID1, 고유ID2는 실제 실행 시 생성되는 UUID를 나타낸다.

gs://버킷/events/date=2026-11-02/hour=09/
  minute=00/part-고유ID1.jsonl
    → evt-001
    → evt-002
  minute=05/part-고유ID2.jsonl
    → evt-003

같은 5분 구간에 다음 저장분이 들어오면 해당 경로에 새로운 고유 이름의 파일을 추가한다. GCS에 업로드한 기존 객체에 클릭마다 한 줄씩 덧붙이는 구조가 아니다.

버퍼와 업로드 처리

event_buffer.py에서 1,000건이 모이거나 30초가 지나면 위 함수를 호출하는 규칙을 구현한다. 30초 조건은 요청이 없어도 실행되도록 별도 주기 작업이 필요하다. 업로드가 성공한 이벤트만 보관 목록에서 제거한다.

초기 실습에서는 메모리에 모을 수 있지만 운영에서는 서버 재시작 시 유실되지 않도록 Pub/Sub 같은 영속 큐와 재시도 구조를 고려한다. 추천 학습용 가공은 저장된 원본을 읽는 다음 단계다.

JSON 전송과 JSONL 파일 내용

클라이언트는 이벤트를 JSON으로 보내고, 저장 프로그램은 여러 이벤트를 한 줄에 하나씩 기록해 JSONL 파일을 만든다.

{"event_id":"e001","event_type":"click","event_time":"2026-11-02T09:01:10+09:00","action":"article_open"}
{"event_id":"e002","event_type":"click","event_time":"2026-11-02T09:02:30+09:00","action":"article_open"}

실시간 처리로 확장

실시간 피처가 필요하면 로깅 서버와 저장 처리 사이에 Pub/Sub 등을 두고 소비 경로를 나눌 수 있다.

로깅 서버 → Pub/Sub ─┬→ GCS 원본 저장 → 배치 가공
                    └→ 실시간 처리 → 최근 관심사 피처 반영

3. 사용자 행동 수집

3.1 서버·클라이언트 전달 항목

수집 단계에는 원본 사실을 기록한다. 클릭 비중·기사 나이·CTR 같은 집계·파생 값은 여기서 보내지 않고 학습 데이터 생성 단계에서 계산한다.

서버 → 로깅 서버: 반환 기사별 기록

요청·사용자·기사 연결과 반환 당시 시각·순서를 남긴다.

항목 JSON 형식 내용
request_id string 목록 조회 요청 ID
impression_id string 기사별 추천 건 ID
user_id string 사용자 ID
article_id string 기사 DB와 연결할 ID
position integer 최종 응답 목록에서의 순서, 1부터 시작
served_at string, ISO 8601 최종 목록을 확정하고 응답을 내보내기 직전에 기록한 시각. 시간대 포함 
{
  "request_id": "req-001",
  "impression_id": "imp-001",
  "user_id": "u001",
  "article_id": "A",
  "position": 1,
  "served_at": "2026-11-02T09:00:00+09:00"
}

기사 분류·언론사·발행 시각은 기존 기사 DB에서 article_id로 연결한다. 프론트에서 다시 보내지 않는다. 기사 정보가 수정될 수 있다면 변경 이력을 보관해 당시 값을 복원한다.

클라이언트 → 로깅 서버: 행동 기록

현재 수집 항목에는 session_id를 사용하지 않는다. 서버에서 받은 값을 그대로 전달하는 항목은 impression_id다. 나머지는 프론트에서 생성·판단·측정한다.

항목 JSON 형식 적용·내용 값 생성 주체 클라이언트의 전달 방법
event_id string 공통, 행동 기록 ID 프론트 이벤트 기록마다 새 ID 생성. 같은 이벤트 재전송 시 기존 ID 유지
event_type string 공통, exposure / click 프론트 감지한 행동 종류를 설정
event_time string, ISO 8601 공통, 발생 시각. 시간 구간이면 시작 시각 프론트 행동 발생·측정 시작 시 브라우저 시각 기록
impression_id string 공통, 기사별 추천 건 ID 웹 Backend 목록 응답에서 받은 값을 카드와 상세 페이지에 유지하고 그대로 전달
page_type string 공통, list / detail 프론트 행동이 발생한 화면에 따라 설정
duration_ms integer exposure, 측정 시간(ms) 프론트 유효 구간 시간을 측정해 전달
ended_at string, ISO 8601 exposure, 측정 종료 시각 프론트 측정 구간 종료 시 브라우저 시각 기록
action string click에만 사용, article_open / like / unlike 프론트 기사 조회·좋아요·좋아요 해제를 구분

exposure는 측정 구간이 끝나면 duration_ms와 함께 전송한다. event_time은 구간 시작, ended_at은 종료다. 다시 보인 구간은 같은 impression_id와 새 event_id로 기록한다. 클릭은 발생 시각만 기록한다. 상세 체류도 event_type=exposure, page_type=detail로 기록하고 시간 구간 필드를 포함한다.

{
  "event_id": "e001",
  "event_type": "exposure",
  "event_time": "2026-11-02T09:00:01+09:00",
  "impression_id": "imp-001",
  "page_type": "list",
  "duration_ms": 3000,
  "ended_at": "2026-11-02T09:00:04+09:00"
}

{
  "event_id": "e003",
  "event_type": "click",
  "event_time": "2026-11-02T09:00:04+09:00",
  "impression_id": "imp-001",
  "page_type": "list",
  "action": "article_open"
}

사용자·요청·기사·추천 순서는 impression_id로 서버 반환 기록에서 찾는다. 프론트는 이를 중복 전송하지 않는다. 로깅 서버는 ID와 시각·값을 검증하며, 재전송된 행동은 event_id로 중복 제거한다.

3.2 이벤트 종류 목록

event_type은 큰 종류, page_type은 발생 화면, action은 클릭의 세부 행동이다. 클릭에는 duration_ms를 넣지 않고, exposure에는 측정 시간을 넣는다.

수집할 행동 event_type page_type action 측정값·발생 기준
목록 기사 카드 노출 exposure list 생략 카드 50% 이상·탭 활성·스크롤 정지 구간의 duration_ms
상세 페이지 노출·체류 exposure detail 생략 상세 페이지가 활성 상태로 보이는 구간의 duration_ms
목록에서 기사 상세 조회 click list article_open 기사 카드를 선택한 시각
목록에서 좋아요 click list like 좋아요가 켜진 시각
목록에서 좋아요 해제 click list unlike 좋아요가 꺼진 시각
상세에서 좋아요 click detail like 상세에 해당 버튼이 있을 경우 수집
상세에서 좋아요 해제 click detail unlike 상세에 해당 버튼이 있을 경우 수집

article_dwell은 ‘상세 기사 페이지에 머문 시간’을 뜻하던 이름이다. 별도 event_type으로 쓰지 않고 exposure + page_type=detail로 통일한다. 상세 체류는 스크롤 중에도 페이지가 보이면 측정한다. 목록의 ‘스크롤 정지 시 측정’ 규칙을 상세에 그대로 적용하지 않는다. 실제 읽었는지까지 확인한 값은 아니다.

목록에서 기사 A를 선택하고 상세를 8초간 본 뒤 좋아요를 누르는 기록은 다음과 같다. 공통 필드 일부는 생략했다.

{"event_id":"e010","event_type":"click","page_type":"list","action":"article_open","impression_id":"imp-001","event_time":"2026-11-02T09:00:04+09:00"}
{"event_id":"e011","event_type":"exposure","page_type":"detail","impression_id":"imp-001","event_time":"2026-11-02T09:00:05+09:00","ended_at":"2026-11-02T09:00:13+09:00","duration_ms":8000}
{"event_id":"e012","event_type":"click","page_type":"detail","action":"like","impression_id":"imp-001","event_time":"2026-11-02T09:00:12+09:00"}

상세에서도 처음 서버에서 받은 impression_id를 유지한다. 좋아요 버튼은 기사 조회와 분리해 처리하여 좋아요 클릭 때문에 article_open까지 중복 기록되지 않게 한다. 해당 UI가 없는 행동은 수집하지 않는다.

3.3 스크롤 시작·종료와 카드 관찰

첫 scroll 발생   → 시작 감지 → 카드별 시간 누적 후 일시정지
scroll 반복 발생 → 스크롤 중 상태 유지
scrollend 발생   → 종료 감지 → 50% 이상 보이는 카드 측정 재개

아래 두 JavaScript 코드는 같은 페이지에서 함께 실행하는 예시다. 첫 코드는 카드 가시성과 구간 시간을 관리하고, 두 번째 코드는 스크롤 시작·종료를 연결한다. HTTP 전송 자체와 상세 체류·클릭 핸들러는 포함하지 않는다.

카드에 서버 응답 ID 연결

<article class="news-card"
         data-impression-id="imp-001">기사 A</article>
<article class="news-card"
         data-impression-id="imp-002">기사 B</article>

JavaScript: 각 카드 관찰 및 시간 측정

const eventQueue = []; // 전송 전 임시 큐. 실제 전송/재시도 구현은 별도
const visibleCards = new Set();
const activeTimers = new Map();
let isScrolling = false;

function startCard(card) {
  if (isScrolling || document.hidden || activeTimers.has(card)) return;
  activeTimers.set(card, {
    monotonicStart: performance.now(),
    eventTime: new Date().toISOString()
  });
}

function stopCard(card) {
  const timer = activeTimers.get(card);
  if (!timer) return;
  activeTimers.delete(card);

  const duration = Math.round(performance.now() - timer.monotonicStart);
  if (duration <= 0) return;
  eventQueue.push({
    event_id: crypto.randomUUID(),
    event_type: "exposure",
    event_time: timer.eventTime,
    impression_id: card.dataset.impressionId,
    page_type: "list",
    duration_ms: duration,
    ended_at: new Date().toISOString()
  });
}

function pauseAll() {
  for (const card of [...activeTimers.keys()]) stopCard(card);
}

function resumeVisible() {
  for (const card of visibleCards) startCard(card);
}

function updateVisibility(entries) {
  for (const entry of entries) {
    const card = entry.target;
    if (entry.isIntersecting && entry.intersectionRatio >= 0.5) {
      visibleCards.add(card);
      startCard(card);
    } else {
      visibleCards.delete(card);
      stopCard(card);
    }
  }
}

const observer = new IntersectionObserver(updateVisibility, {
  root: null, // 페이지 전체 기준. 전용 스크롤 영역이면 해당 요소 지정
  threshold: [0.5]
});

document.querySelectorAll(".news-card").forEach(card => observer.observe(card));
// 무한 스크롤로 추가한 카드에도 observer.observe(newCard)를 호출한다.

document.addEventListener("visibilitychange", () => {
  if (document.hidden) {
    pauseAll();
  } else {
    updateVisibility(observer.takeRecords());
    resumeVisible();
  }
});

window.addEventListener("pagehide", pauseAll);
window.addEventListener("pageshow", resumeVisible);

JavaScript: 스크롤 시작·종료 감지

let stopTimer;
const supportsScrollEnd = "onscrollend" in document;

function handleScrollStop() {
  if (!isScrolling) return;
  // 관찰 콜백에 아직 전달되지 않은 가시성 변경도 반영
  updateVisibility(observer.takeRecords());
  isScrolling = false;
  resumeVisible();
}

document.addEventListener("scroll", () => {
  if (!isScrolling) {
    isScrolling = true;
    pauseAll();
  }
  if (!supportsScrollEnd) {
    clearTimeout(stopTimer);
    stopTimer = setTimeout(handleScrollStop, 300);
  }
}, { passive: true });

if (supportsScrollEnd) {
  document.addEventListener("scrollend", handleScrollStop);
}

한 화면에 두 카드가 50% 이상 보이면 두 카드의 시간이 각각 기록된다. 이는 시선이나 독서를 확인한 값이 아니다. 위 예시는 정지 노출을 측정하므로 빠르게 지나간 카드는 학습용 노출에서 제외되는 정책이다. 스크롤 중 노출도 포함하고 싶다면 별도 가시성 노출 정의를 두고 측정 기준을 구분해야 한다.

브라우저의 관찰 콜백·타이머에는 지연이 있을 수 있어 이 코드는 측정 구조를 설명하는 예제다. 전용 스크롤 컨테이너면 observer의 root와 scroll/scrollend 등록 대상을 함께 변경한다. SPA에서 카드를 제거할 때는 stopCard, unobserve, 상태 제거를 수행해야 한다.

scroll 자체는 서버로 보내지 않고 결과 이벤트만 모아 보낸다. 예를 들어 5초 또는 20건 기준으로 전송할 수 있다. 긴 노출 구간은 주기적으로 구간을 나눠 확정하고, 페이지 이탈 시 전송과 실패 재시도를 구현해야 유실을 줄일 수 있다. 한 HTTP 요청에 여러 이벤트를 담아도 각 이벤트의 event_id는 유지한다.

4. API와 ID 설계

서비스 역할과 배포

웹 Backend와 추천 API는 분리하는 구조로 정리했다. FastAPI는 구현 프레임워크이므로 두 서비스 모두 FastAPI로 만들 수 있다.

웹 Backend
  1. request_id 생성
  2. 같은 request_id를 전달해 추천 API 호출

추천 API
  3. 사용자·후보 피처 조회 및 모델 점수 계산
  4. article_id, 점수 반환

웹 Backend
  5. 기사 DB 조회, 삭제 기사 제외 등 최종 목록 확정
  6. 기사별 impression_id 생성, 최종 position 기록
  7. 최종 반환 목록 로그 기록 및 프론트 응답

프론트
  8. 전달받은 impression_id로 노출·클릭 이벤트 전송

로깅 서버는 웹 Backend의 반환 목록과 프론트 행동을 받아 GCS에 저장한다. GCP에서는 로깅 서버 컨테이너를 GKE의 Pod로 배포할 수 있고, GCS는 클러스터 밖의 저장소다. EKS는 AWS, GKE는 GCP의 관리형 Kubernetes 서비스다.

이 구조는 설계안이다. 앞서 확인한 저장소는 학습 CLI까지였으며 세 API가 구현됐다는 의미는 아니다.

식별자 정의와 유지 규칙

필드 의미 생성 위치 제안
article_id 기사 자체의 ID 기사 생성·DB 저장 단계
request_id 새로운 목록 조회 요청의 ID 웹 Backend 요청 진입 시
impression_id 최종 목록의 기사별 추천 건 ID 웹 Backend가 최종 목록을 확정할 때
event_id 노출·클릭 등 행동 한 건의 ID 프론트에서 이벤트 생성 시
position 최종 목록의 표시 순서 웹 Backend, 프론트 재정렬 시 실제 순서도 기록

한 요청의 목록에서는 같은 기사를 중복 제거하는 것이 기본이다. 매 요청이 고유하고 한 요청 안의 기사 중복이 없다면 request_id + article_id로도 추천 건을 식별할 수 있다. 다만 이번 논의의 최종 결정은 별도 impression_id를 유지하는 것이다.

다음 페이지는 새 조회 요청으로 구분한다. 동일 기사를 새 추천 건으로 반환하면 새 impression_id를 부여한다. 기존 카드가 스크롤로 다시 보이는 경우에는 impression_id를 유지한다. 동일 논리 요청의 재전송에서도 ID를 유지하는 재시도 정책이 필요하다.

5.1 노출·비노출 구분과 label

서버가 기사 10개를 내려줬지만 사용자가 스크롤하지 않아 처음 3개만 봤다고 가정한다.

기사 서버 응답에 포함 화면 노출 클릭 초기 클릭 모델의 학습 처리
A O O O 정답 1
B·C O O X 관찰 시간 종료 후 정답 0
D~J O X X 학습 대상에서 제외

서버 반환은 served, 프론트에서 정의한 실제 노출은 exposure로 구분한다. 미노출을 미클릭 0으로 학습시키면 클릭할 기회가 없던 것을 관심 없음으로 취급하게 된다. 로그가 없으면 유실일 수도 있으므로 처리상으로는 ‘노출 미확인’이다.

정답은 예를 들어 첫 목록 노출 후 30분 이내 기사 조회 여부로 정의한다. 09:40에 처리하고 필요한 로그가 도착했다면:

impression_id 기사 실제 노출 30분 내 클릭 처리
imp-001 A O O clicked=1
imp-002 B O X clicked=0
imp-003 C O X clicked=0
imp-004 D 미확인 X 학습에서 제외

30분이 지나지 않은 행은 보류한다. 센서와 완료 표시만으로 지연 로그 도착을 보장할 수 없으므로 대기 여유·재처리·중복 적재 방지 정책을 정한다. 클릭만 있고 노출이 없는 등의 불일치는 따로 점검한다. exposure 구간의 총 시간은 event_id 중복 제거 후 page_type별로 나눠 합산한다. 목록 노출 시간과 상세 체류 시간을 섞지 않는다.

imp-001 A 금융 0.70 2시간 1
imp-002 B 스포츠 0.10 1시간 0
imp-003 C IT 0.20 3시간 0

피처 예시 원본과 계산
기사 분류 article_id로 기사 DB 연결
추천 당시 기사 나이 served_at − published_at

이번 클릭을 포함해 과거 클릭 비중을 계산하면 안 된다. 추천 당시 알 수 있었던 정보만 피처로 사용한다. 현재 노출에서 얻은 duration_ms·좋아요·상세 체류도 그 추천의 입력으로 넣지 않는다. 이후 추천의 과거 이력 피처로 활용할 수 있다.

서버: 추천 목록 + 기사별 impression_id + 반환 시각 기록
  ↓

  ↓

  ↓

기존 샘플 CSV는 이 가공이 끝난 형태를 흉내 낸 합성 학습 테이블이다. 실제 로그를 결합해 만든 결과는 아니므로, 서비스에는 앞단의 결합·정제 작업을 구현해야 한다.

5.3 모델 학습과 pCTR 예측

학습 입력과 정답

구분 내용
행의 키 impression_id: 연결·추적용이며 모델 입력에서 제외
feature 원본을 결합·집계해 만든 사용자·기사·상황 정보. 모델 설계에 따라 선택
label 관찰 시간 내 클릭 여부 clicked=0/1
모델 출력 특정 사용자·기사·상황에서 클릭할 확률 pCTR
학습 단위 여러 사용자의 행을 모아 하나의 모델 학습

같은 금융 기사라도 u001의 금융 클릭 비중이 0.80, u002는 0.05라면 같은 모델에 들어가는 사용자 피처가 다르므로 예측값도 달라질 수 있다. 사용자 피처·기사·상황이 모두 같으면 같은 점수가 나온다.

pCTR은 어떻게 계산하는가

실제 CTR = 여러 노출의 클릭 수 / 노출 수
pCTR = 학습된 모델이 개별 노출 기회에 대해 출력한 클릭 확률

개별 행의 CTR을 계산해 label로 넣지 않는다. 단순 로지스틱 회귀로 원리를 표현하면:

z = w₁x₁ + w₂x₂ + ... + b
p = 1 / (1 + exp(-z))
손실 = -[y ln(p) + (1-y) ln(1-p)]
y = 실제 클릭 여부(0/1), p = 예측 클릭 확률

모델은 여러 행의 손실이 작아지도록 학습한다. CatBoost 이진 Logloss 모델은 가중치의 단순 합 대신 트리들의 출력 점수를 합쳐 확률로 변환한다. pCTR이 약 15%인 여러 건의 실제 CTR도 약 15%인지 평가해 확률의 적합성을 확인한다.

5.4 Valkey를 이용한 피처 저장·조회와 갱신

추천 요청에서 원본 로그를 매번 정제·집계하는 대신, 배치로 피처를 미리 계산해 Valkey에 저장하고 추천 API가 빠르게 조회한다. 멘토가 Valkey를 제안한 주용도는 이 온라인 피처 저장소다. 웹 Backend 캐시로도 쓸 수 있지만 이는 별도 용도다.

저장소 역할 보관 내용
GCS 원본 로그 보존 서버 반환 목록, 프론트 행동 JSONL
기사 DB 기사 원본 관리 기사 ID, 제목, 분류, 발행 시각 등
BigQuery 오프라인 피처 이력·학습 시점별 피처와 label을 연결할 과거 기록
Valkey 온라인 피처 조회 현재 추천에 사용할 사용자·기사별 피처 
행동 로그·기사 정보
        ↓
배치로 정제·집계해 피처 생성
        ├→ BigQuery: 시점별 피처 이력 → 학습 데이터 생성
        └→ Valkey: 현재 서빙용 피처 → 추천 API가 요청 시 조회

원본 JSON 파일을 클릭 즉시 Valkey에 넘기는 구조가 아니다. 원본 저장과 피처 생성은 별도 단계이며, 전처리는 배치에서 수행한다. Valkey는 기사 DB나 원본 로그 저장소를 대체하지 않는다. 단순 실습에서는 기존 DB의 집계 테이블로도 시작할 수 있지만, 여기서는 멘토가 제안한 Valkey 기반 조회 구조를 정리한다.

저장할 사용자 피처 예시

아래 값과 키 이름은 모델·저장 구조 설명용 예시이며 수집 JSON의 필수 필드가 아니다. 사용자별 집계는 기사 조회 클릭(action=article_open)을 기준으로 한다.

user_id category 과거 7일 클릭 수 해당 분류 클릭 비중 집계 기준 시각 as_of
u001 금융 7 0.70 2026-11-02 10:00:00+09:00
u001 스포츠 1 0.10 2026-11-02 10:00:00+09:00
u001 IT 2 0.20 2026-11-02 10:00:00+09:00

Valkey의 논리적인 키와 값 예시는 다음과 같다. 실제 자료구조·직렬화 방식은 구현 시 정한다.

user:u001
  → 금융 클릭 비중 0.70, 스포츠 0.10, IT 0.20, 집계 기준 시각

article:A
  → 기사 분류, 발행 시각, 기사별 집계값 등 선택한 피처

추천 요청에서 조회하는 흐름

웹 Backend → 추천 API: user_id와 요청 컨텍스트 전달
                     ↓
              user_id로 Valkey 사용자 피처 조회
              후보 article_id로 기사 피처 조회
                     ↓
              현재 사용자 × 후보 기사별 입력 구성
                     ↓
              모델 점수 계산 → 순위 결정

후보 기사 A가 금융이면 u001의 금융 클릭 비중 0.70을 붙이고, 기사 B가 스포츠이면 0.10을 붙인다. 기사 정보·집계 피처는 필요에 따라 Valkey에 준비하고, 기사 원문은 기사 DB에 유지한다. 현재 기사 나이처럼 간단한 값은 요청 시각과 발행 시각으로 계산할 수 있다. 후보 기사마다 별도 네트워크 왕복이 발생하지 않도록 여러 기사 피처를 묶어 조회하는 방식도 고려한다.

피처 갱신·모델 학습·실시간 추론은 서로 다르다

작업 변경하는 것 주기 예시
피처 갱신 사용자 상태·기사 집계 등의 입력값 1시간마다
모델 학습 트리·가중치 등 예측 규칙 하루마다
실시간 추론 현재 모델과 준비된 피처로 요청별 점수 계산 요청마다

주기는 확정값이 아니라 예시다. 실시간 추론은 요청에 바로 예측한다는 뜻이며, 직전 클릭까지 피처에 즉시 반영한다는 뜻이 아니다. 학습 주기와 피처 갱신 주기는 독립적으로 정할 수 있다. 같은 모델이어도 사용자 피처가 갱신되면 추천 결과가 달라질 수 있다.

10:00  배치로 피처 계산·Valkey 반영 완료
10:51  추천 요청 → 10:00에 반영한 피처 + 현재 배포 모델로 예측
10:52  새 클릭 발생 → 원본 로그에 기록
11:00  다음 배치 반영 완료 → 이후 추천부터 새 피처 사용

마지막 예시의 반영 시각은 설명을 위해 단순화했다. 실제로는 집계와 전송에 시간이 걸리며, 그동안은 이전 피처를 사용한다. 한 시간 주기라 해도 지연 도착·처리 지연으로 피처 지연이 한 시간보다 커질 수 있다.

배치 부하와 기본값

매번 전체 원본을 처음부터 읽는 대신, 사용자·분류·시간별 클릭 수를 집계해 재사용할 수 있다.

원본 클릭 로그
  → 사용자·분류·시간별 클릭 수 집계
  → 최근 7일 집계값 합산
  → 분류별 클릭 비중 계산
  → 갱신된 값을 Valkey에 반영
  • 새 시간 구간을 추가하고, 7일 창에서 벗어난 구간을 제외한다. 새 클릭이 없는 사용자도 창의 이동으로 값이 바뀔 수 있다.
  • 실제 가능한 주기는 사용자 수·이벤트 수·피처 복잡도·배치 실행 시간·Valkey 반영 시간을 측정해 정한다. 1시간 주기가 무조건 가능하다는 뜻은 아니다.
  • 집계 기준 시각과 실제 반영 시점을 관리하고, 사용자 피처 묶음이 중간 상태로 섞이지 않게 갱신한다.
  • 이력이 없거나 전체 클릭 수가 0인 경우 분류별 비중을 0으로 두는 등 기본값을 정한다. Valkey 키가 없을 때도 정해진 대체값을 적용하고, 학습에서도 같은 정책을 재현한다.

5.5 Point-in-time join: 추천 당시 피처로 학습

Point-in-time join은 과거 추천 기록에 ‘그 추천 시점에 사용 가능했던 피처’를 연결하는 것이다. 사용자 ID만으로 지금의 최신 값을 붙이는 것과 다르다.

시간별 예시

시각 상황 u001의 금융 클릭 비중
10:00 피처 계산·Valkey 반영 완료 0.70
10:51 금융 기사 A 추천 모델 입력은 0.70
10:52 기사 A 조회 클릭 label=1
11:00 이후 행동을 반영한 피처 갱신 0.80
14:00 다시 갱신 0.90
15:00 10:51 추천 건으로 학습 데이터 생성 당시 값인 0.70을 연결 
올바른 행: 10:51 추천 + 당시 사용한 피처 0.70 + clicked=1
잘못된 행: 10:51 추천 + 14:00의 최신 피처 0.90 + clicked=1

0.90에는 추천 이후 행동이 포함될 수 있다. 당시 몰랐던 정보를 학습 입력에 넣으면 데이터 누수가 발생한다. 또한 학습 때와 실제 추천 때의 입력 조건이 달라진다.

집계 기준 시각과 사용 가능 시각 구분

시각 정보 의미
as_of 어느 시점의 과거 이력을 기준으로 집계했는가
available_at 피처가 온라인 저장소에 반영돼 실제로 조회 가능해진 시각
추천 시각 해당 모델 추론에 사용할 피처를 선택한 시각

예를 들어 10:00 기준 집계라도 실제 Valkey 반영이 10:55였다면 10:51 추천에는 사용할 수 없었다. 이전에 반영된 값을 찾아야 한다.

10:51 추천 기록
  → 동일 사용자·기사의 피처 이력 조회
  → 10:51 이전에 실제 사용 가능했던 값으로 제한
  → 그중 당시 서빙 정책이 선택할 최신 값을 연결
  → 클릭 label과 결합해 학습 행 생성

학습 이력은 BigQuery 등에 보관하고, Valkey 최신 값만 다시 읽어 과거 학습 행에 붙이지 않는다. 사용자 피처와 기사 피처 모두 같은 원칙으로 연결하며, 신규 사용자나 키 누락 때 적용한 기본값도 재현해야 한다.

실제 조회 직후 갱신이 발생하면 응답 반환 시각(served_at)과 피처 선택 시각이 어긋날 수 있다. 정확히 재현하려면 피처를 선택한 시각·실제 사용한 피처 묶음의 식별 정보 또는 실제 입력 스냅샷을 추론 기록에 남기는 방식을 설계해야 한다. 이는 서버·프론트의 최소 수집 JSON과는 별도의 학습 재현용 기록이다. Valkey 반영과 오프라인 이력 사이의 시간·값도 일치하도록 관리해야 한다.

5.6 실제 추천 요청의 입력과 계산

추천 시에는 새 impression_id가 아직 없어도 된다. user_id로 과거 사용자 피처를 조회하고 후보 article_id로 기사 피처를 가져와 현재 사용자×후보 기사마다 한 행을 만든다.

사용자 후보 기사 category 해당 분류 클릭 비중 현재 기사 나이
u001 A 금융 0.70 2시간
u001 B 스포츠 0.10 1시간
u001 C IT 0.20 3시간

이것은 일부 피처만 보여주는 표다. 5.4의 Valkey 사용자·기사 피처와 요청 시 계산값을 결합하고, 학습 때와 동일한 전체 피처 컬럼·정의를 사용한다.

# candidates: 현재 사용자와 후보 기사별 피처를 담은 DataFrame
# FEATURES: 학습과 동일한 전체 입력 피처 이름 목록
# model: 학습된 CatBoostClassifier
candidates["pctr"] = model.predict_proba(candidates[FEATURES])[:, 1]
recommended = candidates.sort_values("pctr", ascending=False).head(5)

u001 + 기사 A 피처 → 모델 → pCTR 0.35
u001 + 기사 B 피처 → 모델 → pCTR 0.04
u001 + 기사 C 피처 → 모델 → pCTR 0.18
                           ↓
                       A → C → B

기사 전체 10,000개를 점수화할 수도 있지만, 초기 설계는 후보를 먼저 추린 뒤 개인별로 정렬한다.

기사 10,000개
  → 최근 발행·서비스 가능 조건
  → 이미 클릭한 기사·현재 피드에서 반환한 기사 제외
  → 후보 200개(예시)
  → 사용자×기사별 피처로 점수 계산
  → 상위 5개 반환

후보를 5개만 가져오면 모델은 그 5개의 순서만 바꿀 수 있다. 후보 폭과 제외 정책은 품질·응답 시간을 측정해 정한다. 웹 Backend가 최종 반환 목록에 impression_id를 부여하면 이후 행동이 다음 학습 데이터로 이어진다.
