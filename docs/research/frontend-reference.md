# 프론트엔드 개발 참고 자료

작성일: 2026-10-30. 이 문서는 프론트엔드 구현을 맡는 개발자의 작업 시작 자료다. [전체 유사 프로젝트 조사](similar-projects.md)를 보완한다. 공개 소스와 로컬 소스 확인 결과, 적용 제안, 미확정 계약을 구분한다. 이 작업에서는 앱 코드를 수정하거나 실행하지 않았다.

## 현재 구현과 범위

실제 화면 코드는 인접 저장소 `asac-news-frontend`에 있다. 이 문서 경로를 기준으로 `../../asac-news-frontend`다. 다음 경로는 해당 프론트엔드 저장소 기준이다. 개발 시작 시 저장소 상태와 지침을 다시 확인한다.

| 파일 | 확인한 역할 | 다음 작업의 연결 지점 |
|---|---|---|
| `src/app.js` | 카드, 피드 상태, 기사 상세, 해시 경로, 스크롤 복원. 요청 번호로 늦게 도착한 응답 무시 | 카드별 노출 관찰, 클릭 수집, 화면 교체 시 관찰 해제 |
| `src/service.js` | 가상 독자의 샘플 피드 생성, 로딩·오류·빈 결과 시연, 기사 조회 | 실제 추천 API 응답을 화면용 데이터로 변환 |
| `src/visitor.js` | 동일 출처 방문자 API 호출, 저장 시작과 삭제, 쿠키 기반 재방문 | 수집 가능 상태를 이벤트 계층과 공유하는 계약 필요 |
| `src/data.js` | 가상 기사와 독자 데이터 | 실제 데이터와 샘플 데이터 구분 유지 |
| `src/style.css` | 화면 스타일 | 상태 화면과 모바일 표시 검증 |
| `package.json` | 외부 프론트엔드 프레임워크 의존성 없는 Node 기반 검사·빌드 | 기존 도구 유지 여부 판단의 출발점 |

현재 피드의 가상 독자 ID와 실제 브라우저 방문자 ID는 별개다. 샘플 추천 순서를 실제 행동 기반 추천으로 보고하면 안 된다. `visitor.js`와 기사 상세에는 클릭·읽기 시간을 수집하지 않는다는 안내가 있다. 행동 수집을 구현할 때 실제 동작과 안내 문구를 함께 맞춰야 한다.

현재 확인한 방문자 호출은 `/api/v1/visitors/me`, `/api/v1/visitors/bootstrap`, `/api/v1/visitors/reset`이다. 쿠키는 서버가 관리한다. 프론트엔드에서 인증 표식을 읽거나 이벤트 본문에 복사하지 않는다. 식별 표식 유효기간은 README 기준 30일이다.

사용자 범위는 비로그인 뉴스 이용, 노출·클릭 수집, 추후 배치 추천 연결이다. 초기 관심사 입력은 MVP에서 제외했다. 화면은 존재하며 수집 API, 클라우드 저장, 추천 API, CTR 모델은 연결 전이다.

## 프론트엔드 적용 방향

기존 JavaScript 화면을 출발점으로 삼는다. 조사 대상의 React 의존성을 그대로 추가하지 않는다. 새로운 프레임워크 도입은 화면 규모와 팀 유지보수 요구가 확인되면 별도로 판단한다.

| 책임 | 현재 위치 또는 제안 위치 | 경계 |
|---|---|---|
| 기사·추천 표시 | 현재 `app.js` | 기사 ID와 노출 문맥을 카드에 연결. 모델 계산은 하지 않음 |
| 피드 데이터 접근 | 현재 `service.js` | 샘플과 API 데이터를 같은 화면 모델로 변환. 샘플 출처 표시 유지 |
| 방문자 상태 | 현재 `visitor.js` | 저장 허용 여부, 만료·삭제 상태를 수집 계층에 전달 |
| 노출·클릭 수집 | 제안 `tracking.js` | 관찰, 이벤트 생성, 중복 방지. DOM 교체 시 정리 |
| 이벤트 전송 | 초기에는 수집 모듈 내부 | 배치와 재시도. 복잡해질 때만 별도 파일로 분리 |

이 표의 신규 모듈은 설계 제안이다. 현재 구현된 파일로 오해하지 않는다. 브라우저는 수집 API에만 연결한다. Cloud Storage와 BigQuery 접근 자격은 브라우저에 두지 않는다.

## 백엔드와 맞출 데이터 계약 초안

아래 필드와 경로는 제안이며 구현된 API 명세가 아니다. 구현 전에 백엔드 담당자와 ID 발급 주체, 필수 필드, 응답·오류 형식을 맞춘다.

### 추천 응답의 화면용 정보

| 필드 | 의미 |
|---|---|
| `recommendation_id` | 생성된 추천 결과의 ID. 배치 결과라면 재조회에도 같을 수 있음 |
| `generated_at` | 추천 생성 시각. UTC ISO 8601 |
| `strategy` | 최신·인기·개인화·샘플 등 실제 생성 방식 |
| `items[].article_id` | 안정적인 기사 ID. 제목이나 배열 인덱스로 대체하지 않음 |
| `items[].rank` | 추천 결과 내 순위. 1부터 시작 |
| 기사 표시 정보 | 제목, 요약, 카테고리, 게시 시각, 이미지와 대체 텍스트, 본문 또는 상세 조회 정보 |
| `items[].reason` | 서버가 제공할 수 있을 때만 표시하는 추천 근거 |

추천 결과 ID와 화면 노출 묶음 ID를 구분한다. 같은 배치 결과를 다시 열어도 새로운 화면 방문이면 노출 문맥은 다르다. 화면에서 필터링하면 추천 순위와 실제 표시 위치가 달라질 수 있으므로 둘 다 보존한다.

### 행동 이벤트의 정보

| 필드 | 의미와 생성 규칙 제안 |
|---|---|
| `schema_version` | 이벤트 형식 버전 |
| `event_id` | 개별 이벤트의 임의 ID. 재전송 시 유지하여 서버 중복 제거에 사용 |
| `event_type` | MVP는 `impression` 또는 `click` |
| `occurred_at` | 발생 시각, UTC ISO 8601. 서버는 수신 시각도 별도로 저장 |
| `page_view_id` | 화면 방문 문맥. 발급·복원 규칙은 합의 필요 |
| `feed_view_id` | 해당 피드·카테고리 노출 묶음 ID |
| `recommendation_id` | 추천 응답 ID. 샘플에는 샘플 표시를 함께 보존 |
| `article_id` | 대상 기사 ID |
| `recommendation_rank` | 원래 추천 순위, 1부터 시작 |
| `display_position` | 해당 화면에서의 실제 위치, 1부터 시작 |
| `placement` | 홈 피드 등 노출 영역 |
| `impression_id` | 개별 카드 노출 ID. 연결할 수 있는 클릭에서 참조 |

실제 방문자 ID는 서버가 쿠키로 확인한다. 클라이언트가 보낸 독자 ID를 신원 근거로 신뢰하지 않는다. 가상 독자 ID를 실제 방문자의 행동에 섞지 않는다. 노출 기준 충족 전에 빠르게 클릭했다면 클릭은 보존하고, 기준을 충족한 노출을 임의 생성하지 않는다. 연결되지 않은 클릭의 학습 처리 규칙은 배치 담당자와 정한다.

제안 경로는 `POST /api/v1/events`다. 서버의 부분 성공 여부, 승인한 이벤트 ID 목록, 요청 크기 제한, 재시도 가능한 오류는 미확정이다. 추천·기사 조회 경로도 아직 확정하지 않았다.

## 노출·클릭의 브라우저 처리 초안

아래 수치는 측정된 최적값이나 확정 요구사항이 아니다. 구현 시 검토할 초안이다.

| 항목 | 제안 동작 | 확인할 예외 |
|---|---|---|
| 노출 | 카드 면적 50% 이상이 연속 1초 동안 뷰포트와 교차하고 탭이 보일 때 기록 | 화면보다 큰 카드, 모달 가림, 빠른 스크롤, 작은 화면 |
| 중복 | 같은 `feed_view_id + article_id + display_position`에서 한 번 기록 | 상세에서 돌아올 때 기존 문맥 유지. 실제 새 피드 조회는 새 ID |
| 클릭 | 기사 링크 활성화를 기록하고 기사 이동은 즉시 수행 | 키보드 Enter, 새 탭 열기, 보조 클릭의 지원 범위를 정함. 기본 이동을 차단하지 않음 |
| 직접 상세 접근 | 상세 방문을 카드 클릭으로 꾸미지 않음 | 공유 링크와 새로고침 |
| 탭 숨김 | 노출 연속 시간 초기화, 대기 이벤트 전송 시도 | 탭 복귀 시 다시 판정 |
| 화면 교체 | observer와 타이머 정리 | 이전 화면의 지연 콜백이 새 피드 이벤트를 만들지 않도록 문맥 검사 |
| 방문자 삭제 | 대기 중 수집 중단과 큐 제거 | 이미 서버에 전송한 행동의 삭제 범위는 별도 서버 계약 |

[Intersection Observer API](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)는 교차 비율을 관찰한다. 기본 모드는 다른 요소에 가려졌는지까지 보장하지 않으므로 실제 주의나 읽기를 증명하는 값으로 표현하지 않는다. [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)로 숨긴 탭의 시간을 제외한다.

일반 전송에는 응답을 확인할 수 있는 fetch를 사용한다. 탭이 숨겨질 때는 [sendBeacon](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon)으로 작은 배치를 보낼 수 있다. 반환값 true는 전송 큐 등록이며 서버 저장 성공 확인이 아니다. 종료 시 전송은 손실 가능성이 있으므로 전달 보장을 주장하지 않는다. 재시도는 같은 event_id를 유지하고 서버도 중복을 제거해야 한다.

행동 저장을 허용하지 않은 상태에는 수집하지 않는 방향을 제안한다. 브라우저 재시도 큐는 우선 메모리로 제한하고 크기·횟수 상한을 둔다. 지속 저장을 추가한다면 만료·삭제·방문자 교체 규칙을 먼저 정한다. 체류 시간은 추후 범위이며 도입 시 화면 활성 시간의 밀리초로 정의하고 실제 독서 시간과 구분한다.

| 상세 복귀 | 피드·카테고리·스크롤 복원 | 복원 때문에 같은 문맥의 노출이 중복되지 않음 |

## 구현 순서와 검증 자료

1. 기존 앱을 실행해 피드·상세·뒤로 가기·방문자 저장과 삭제를 확인한다. 실제 작업 전에 해당 저장소의 지침을 읽는다.
2. 데이터 계약을 확정하고 샘플 피드와 실제 방문자의 식별자를 분리한다. 이벤트 예시와 API 응답 예시를 계약 자료로 남긴다.
3. 로컬 수집 API와 노출·클릭 수집을 연결한다. 서버에 저장된 실제 이벤트로 카드별 연결과 중복 여부를 확인한다.
4. 수집 실패·재시도·삭제·숨긴 탭·빠른 클릭·상세 복귀를 브라우저에서 검증한다. 클라이언트와 서버의 이벤트 ID를 대조한다.
5. 추천 API를 `service.js`에 연결한다. 기본 추천과 개인화 추천의 상태·근거·생성 시각을 실제 응답에 맞게 표시한다.

현재 프론트엔드 package.json의 명령은 `npm run check`, `npm test`, `npm run build`, `npm start`다. README의 Docker 실행은 `docker compose up -d --build --wait`이고 접속 주소는 `http://127.0.0.1:8080/`이다. 현재 Compose는 Nginx 80에서 정적 화면과 FastAPI 전달을 제공한다. Node 개발 서버는 `npm start`로 별도 실행한다. 이 문서 작성 중 명령을 실행하지 않았다. 자동 검사에 더해 실제 브라우저와 서버 저장 결과로 수집 동작을 증명해야 한다.

## 다음 개발 세션의 시작점

이 문서와 `asac-news-frontend/README.md`, `docs/implementation/anonymous-visitor-implementation.md`를 읽고 현재 소스를 다시 확인한다. 기존 화면과 방문자 식별을 기준으로 노출·클릭 계약부터 확정한다. 초기 관심사 입력은 추가하지 않는다. 수집 성공, 추천 연결, 성능 개선은 각각 실제 결과가 있을 때만 완료로 보고한다.

남은 결정은 노출 기준, 노출 문맥 복원 규칙, 클릭 관찰 기간, 수집 허용 안내, 서버 이벤트 승인 방식이다. 위 제안값을 확정 사항으로 취급하지 않는다. 코드 재사용 시 파일별 라이선스와 의존성을 확인한다.
