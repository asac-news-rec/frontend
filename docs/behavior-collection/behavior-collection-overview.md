# 뉴스 이용 기록 수집 계획 · 팀 회의용

작성일: 2026-11-02 · 버전 0.3 · 구현 전 통합 제안

[백엔드 논의 자료](../meetings/2026-10-31/news_recommendation_discussion.html)의 2~4절과 5.2절을 반영했다. 원본은 논의 정리이며 전체 회의 확정본이나 구현 완료 보고가 아니다. 이 문서는 그 내용을 프론트엔드 작업에 연결한 제안이다. 정확한 연결 규칙은 [프론트엔드 명세](behavior-collection-frontend-spec.md)에 있다.

## 1. 이번에 바뀐 내용

기존 자료와 백엔드 자료는 전체 흐름이 같다. 브라우저가 행동을 보내고 서버가 원본을 저장한 다음, 배치로 분석한다. 다만 행동의 이름·식별자·시간 측정 방식은 달라서 백엔드 형식으로 맞췄다.

| 항목 | 이전 프론트엔드 초안 | 이번 통합안 |
|---|---|---|
| 행동 연결 | 피드 ID·기사 ID·노출 이벤트 ID 등을 전송 | 서버가 준 기사별 impression_id를 그대로 전달 |
| 목록 노출 | 50% 이상 1초가 되면 1회 | 50% 이상 보이고 탭이 활성화되어 있으며 스크롤이 멈춘 구간의 시간을 기록 |
| 상세 체류 | 별도 article_dwell, 10초마다 증가분 보고 | exposure라는 같은 종류로 기록하고 detail 화면으로 구분 |
| 전송 시점 | 클릭 즉시, 체류는 주기적으로 확정 | 클릭 즉시, 노출·체류는 구간 종료 즉시 개별 전송 |
| 반복 노출 | 같은 피드에서 1회만 생성 | 다시 보이면 새 구간 기록. 분석에서 같은 추천 건으로 합침 |
| 좋아요 | 행동 로그 대상에서 제외 | like·unlike로 구분해서 기록. 기사 조회 클릭과 분리 |

기존의 1초 최소 기준과 10초 정기 보고는 현재 통합안에서 제거했다. 장시간 화면을 켜 두거나 강제 종료하면 종료 전까지의 구간이 유실될 수 있다. 이를 줄이는 중간 보고는 백엔드와 별도로 합의할 보완안이다.

## 2. 실제로 어떤 기록이 남나요?

서버가 A 기사를 내려줄 때 추천 건 번호 `imp-A`를 함께 준다고 가정하자. 이 번호는 “화면에 실제로 보였다”는 뜻이 아니라 “이번에 반환한 A 기사”를 가리킨다.

1. A 카드가 절반 이상 보이고 스크롤이 멈춘 상태로 3초 유지된다.
2. 스크롤을 시작하면 “imp-A가 목록에서 3초 보였다”를 즉시 전송한다.
3. 다시 돌아와 2초 보면 새 행동 번호로 2초 구간을 보낸다. 추천 건 번호는 계속 imp-A다.
4. A를 누르면 “imp-A의 기사 열기”를 즉시 전송한다.
5. 상세를 8초 보고 다른 탭으로 이동하면 “imp-A가 상세에서 8초 보였다”를 즉시 전송한다.
6. 좋아요 저장이 성공하면 “imp-A의 좋아요”를 별도로 보낸다. 기사 열기 클릭이 또 생기지는 않는다.

분석에서는 목록 노출 시간 5초, 상세 체류 8초로 구분한다. 같은 추천 건의 노출 구간이 두 개라도 클릭률 분모를 두 번 늘리지 않는다. 다른 탭에 있는 시간은 제외한다. 상세 화면에서는 스크롤 중에도 시간을 측정한다. 이 기록은 시선이나 실제 독서를 확인한 값이 아니다.

## 3. 5분 파티션과 FLUSH는 다릅니다

이전 설명에서 “5분 단위로 묶어 저장”이라고 표현한 부분을 아래처럼 구분한다.

| 구분 | 백엔드 자료의 예시 | 의미 |
|---|---|---|
| 브라우저 전송 | 이벤트 확정 즉시 | JSON 한 건씩 API에 전송 |
| 저장 파티션 | 발생 시각 기준 5분 | 원본 파일을 어느 경로에 넣을지 결정 |
| FLUSH | 1,000건 또는 30초 | 서버가 모은 기록을 JSONL 파일로 저장 |
| 가공 주기 | 1시간 | 원본을 읽어 정제·집계하는 간격 |

09:02와 09:04에 발생한 기록은 minute=00 경로, 09:07 기록은 minute=05 경로에 들어간다. 같은 경로에 파일이 여러 개 생길 수 있다. 5분이 끝날 때까지 브라우저나 서버가 반드시 기다린다는 뜻은 아니다. 1,000건·30초·1시간은 백엔드 자료의 설명용 숫자이며 확정값이 아니다.

```text
웹 백엔드: 기사 목록과 추천 건 번호 반환 → served 원본 기록
프론트엔드: 노출·클릭·체류 구간 측정 → actions JSON 즉시 전송
                                      ↓
로깅 서버: 검증 → 임시 보관 → 발생 시각별 5분 경로로 JSONL 저장
                                      ↓
GCS served/actions 원본 → Airflow 조율 → BigQuery 결합·검증
                                      ↓
학습·피처 갱신 → 추천 API가 다음 요청에 사용
```

현재 앱은 가상 기사, 방문자 쿠키, 좋아요 저장과 간단한 좋아요 기반 정렬까지 구현된 상태다. 위 수집·클라우드·학습 경로는 아직 구축하지 않았다.

## 4. 프론트엔드와 서버의 역할

| 담당 영역 | 해야 할 일 |
|---|---|
| 프론트엔드 | 서버 ID를 카드·상세에 유지, 시간 측정, 단건 즉시 전송, 실패 재시도, 수집 해제 시 중단 |
| 웹 백엔드 | request_id와 기사별 impression_id 발급, 최종 순서와 사용자 연결, served 로그 보존 |
| 로깅 서버 | 이벤트·소유자 검증, 수신 응답, 버퍼·FLUSH·GCS 저장·재시도 |
| 데이터 담당 | Airflow 조율, 원본 적재·중복 제거, 노출 구간 결합, 품질 확인·학습 표본 생성 |
| 공동 | API 계약, 수집 선택, 삭제 범위, 실패·유실 기준 합의와 실제 연결 검증 |

프론트엔드는 GCS 파일이나 Airflow 센서를 만들지 않는다. JSONL 변환·5분 경로 계산도 서버가 한다. 추천 모델·Valkey를 직접 호출하지 않고 웹 백엔드가 반환한 목록을 표시한다. 새 행동이 즉시 전송되어도 추천에 즉시 반영되는 것은 아니다.

## 5. 센서는 무엇을 확인하나요?

센서는 필요한 파일이 도착했는지 같은 조건을 기다리는 역할이다. 파일이 있다는 사실만으로 중복·누락·잘못된 시간이 없다고 판단할 수는 없다. GCS 존재 확인 센서와 업로드 변화가 멈췄는지 확인하는 센서도 서로 다르다. [Airflow GCS 센서 공식 문서](https://airflow.apache.org/docs/apache-airflow-providers-google/stable/_api/airflow/providers/google/cloud/sensors/gcs/index.html)

우리 통합안은 파일 준비 확인 다음에 필드·시간·중복·served/actions 연결을 검사하는 작업을 분리한다. 이벤트가 없는 구간도 정상일 수 있으므로 “파일이 없음 = 오류”로 처리하지 않는다. 완료 표시·건수 정보와 지연 도착 재처리 기준은 데이터 담당자가 설계한다. 프론트는 시험 이벤트 ID를 제공해서 저장·분석 결과까지 추적하는 검증에 참여한다.

## 6. 연결 전에 확인해야 할 사항

| 결정할 내용 | 필요한 이유와 제안 |
|---|---|
| API 성공의 의미 | 서버 메모리에만 들어간 기록은 재시작 때 사라질 수 있다. 영속 보관을 확인한 뒤 성공하는 방식을 권장한다. 실습용 메모리 수락은 유실 허용 모드로 명시해야 한다. |
| 상세 직접 진입 | 피드를 거치지 않으면 impression_id가 없다. 서버의 상세 컨텍스트 발급을 검토하고, 정해지기 전에는 연결 ID를 임의 생성하지 않는다. |
| 수집 선택·삭제 | 기존 좋아요 저장 선택을 행동 수집 허용으로 자동 해석하지 않는 제안을 유지한다. 서버·원본·분석 데이터 삭제 범위도 합의한다. |
| 필터·다음 페이지 | 최종 표시 순서는 서버 기록과 같아야 한다. 실제 API 연결에서는 카테고리 필터를 서버로 전달하는 안을 권장한다. |
| 측정의 세부 기준 | 스크롤 종료 미지원 브라우저의 300ms 보조 판정, 창 포커스 기준, 긴 구간 중간 보고는 추가 합의가 필요하다. |
| 지연·보관 | 클릭 관찰 30분은 예시다. 지연 허용·보관·삭제 기한도 운영 계약으로 확정해야 한다. |

현재 메모리 재시도 기록의 새로고침 유실 가능성, 같은 이벤트 ID로 재전송하는 원칙은 유지한다. 단건 전송 주소와 정확한 성공 응답 형식은 아직 확정되지 않았다.

## 7. 다음 작업의 완료 기준

먼저 백엔드와 실제 피드 응답·행동 JSON·수신 응답을 맞춘다. 그다음 목록 노출 → 기사 열기 → 상세 체류 → 좋아요 한 번을 같은 impression_id로 추적한다. 재전송해도 분석 결과가 늘어나지 않고, 다시 보인 구간은 정상적으로 추가되는지 확인한다. 마지막으로 실제 GCS 파일과 BigQuery 행을 확인해야 수집 경로가 연결되었다고 말할 수 있다.

이번 변경은 문서만 수정했다. 백엔드 원본 자료와 앱 코드는 변경하지 않았다.
