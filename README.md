# 사이 뉴스 화면 초안

합성 로그 실습의 페르소나 5명과 입력 생성 명령은 [합성 로그 에이전트](docs/behavior-collection/synthetic-logging-agent.md)를 참조하세요. 현재 관심사 이름은 프런트엔드 시연 데이터 기준이며 백엔드 DB 카테고리는 확인되지 않았습니다.

## 실제 뉴스 백엔드 화면 확인

백엔드 저장소의 API(`POST /user/anonymous`, `POST /news/feed`, `PUT/DELETE /news/{article_id}/like`)를 같은 출처의 Node 서버 프록시로 연결합니다. 백엔드 API가 `127.0.0.1:8000`에서 실행 중이면 다음과 같이 시작합니다.

```powershell
$env:NEWS_BACKEND_URL='http://127.0.0.1:8000/'
npm start
```

브라우저에서 `http://127.0.0.1:4173/`을 엽니다. 기본 화면이 백엔드 피드를 사용합니다. 백엔드의 Nginx `127.0.0.1:8080`을 사용할 때는 `NEWS_BACKEND_URL='http://127.0.0.1:8080/api/'`로 설정합니다. Docker 프론트엔드에서 호스트의 백엔드로 접근할 때는 `NEWS_BACKEND_URL='http://host.docker.internal:8000/'`을 설정하고 `docker compose up -d --build --wait`로 실행합니다. 실제 접속 주소는 이 PC와 백엔드 담당자가 접근 가능한 호스트 주소에 맞춰야 합니다. 기존 샘플 화면은 `/?feed=sample`에서 별도로 확인할 수 있습니다.

DB의 `image_url`이 백엔드 저장소의 기본값인 `http://localhost:8001/`을 가리키면 아래 Docker 실행 절차의 이미지 서버도 켭니다. 이미지가 없거나 접근할 수 없으면 화면은 기존 일러스트를 표시합니다.

백엔드 모드는 브라우저에 `reader_id`를 저장하며 백엔드 피드의 `items`, `next_offset`, `is_liked`를 화면에 사용합니다. 목록은 백엔드의 최신순이며 학습된 추천 순위가 아닙니다. 백엔드 기사는 상세 새로고침 시 목록 캐시가 없어 다시 피드에서 열어야 합니다. 이 모드의 좋아요는 백엔드 API에 저장됩니다. 이전 샘플 화면의 방문자 쿠키와 로컬 SQLite 좋아요는 별도입니다. 실제 백엔드와 DB가 기동되지 않았다면 연결 오류를 표시하며 샘플 기사로 대체하지 않습니다.

2026-11-05에 전달된 `news_api_spec (1).xlsx`는 피드 응답 최상위 `reader_id`를 필수로 명시하지만, 백엔드 담당자는 이 필드가 없는 응답이 맞다고 확인했습니다. 현재 `app/main.py`의 성공 응답은 `request_id`, `served_at`, `items`, `next_offset`입니다. 프론트는 최상위 `reader_id`를 요구하지 않습니다. 문서의 해당 필드는 백엔드 명세에서 바로잡아야 합니다.

한국어 뉴스 서비스의 팀 검토용 화면입니다. `사이 뉴스`는 교체 가능한 임시 이름입니다. 기본 화면은 백엔드 뉴스 API에 연결되며, 현재 DB의 기사는 합성 데이터입니다. 학습된 추천 모델과 행동 수집 서버는 연결되지 않았습니다. 아래의 샘플 피드·방문자 설명은 `/?feed=sample` 모드에 해당합니다.

## Docker로 실행

집 Mac에서 프론트엔드와 백엔드를 함께 시연하는 절차는 [Mac Docker 시연 안내](docs/mac-docker-demo.md)를 참고하세요.

태원님 PC에서는 다음 순서대로 확인할 수 있습니다. 프론트엔드와 백엔드 저장소는 같은 PC에 두고 Docker Desktop을 실행합니다.

1. 백엔드 저장소의 안내에 따라 API와 DB를 먼저 실행합니다. 브라우저에서 `http://127.0.0.1:8000/health`가 `{"status":"ok","database":1}`을 반환하고 기사 데이터가 적재되어 있어야 합니다.
2. 프론트엔드 저장소에서 `feat/7-backend-integration` 브랜치로 전환한 뒤 아래 명령을 실행합니다.

```powershell
git switch feat/7-backend-integration
$env:NEWS_BACKEND_URL='http://host.docker.internal:8000/'
docker compose up -d --build --wait
```

3. 브라우저에서 **http://127.0.0.1:4181/** 을 엽니다. 기사 제목과 본문이 나오면 연결된 것입니다. Docker 컨테이너 내부의 4173 포트가 PC의 4181 포트에 연결됩니다. Docker로 확인할 때 PC의 4173을 따로 열거나 `npm start`를 실행할 필요가 없습니다. Origin 검증을 위해 `localhost` 대신 `127.0.0.1`을 사용합니다.

4. 기사 썸네일 URL이 `http://localhost:8001/`인 경우, 백엔드 저장소 폴더에서 아래 명령으로 이미지 서버를 한 번 실행합니다. 이 서버는 백엔드의 이미지 파일을 읽기 전용으로 제공합니다.

```powershell
docker run -d --name asac-news-backend-images -p 127.0.0.1:8001:80 -v "${PWD}/generate/output_with_thumbnail:/usr/share/nginx/html:ro" nginx:stable-alpine
```

이미지 서버를 다시 시작할 때는 `docker start asac-news-backend-images`를 사용합니다. 이미지 서버를 실행하지 않아도 기사 제목·본문과 좋아요는 동작합니다. 프론트엔드 이미지 빌드 중 문법 검사·테스트·정적 빌드가 실행됩니다.

화면이 연결 오류를 보이면 백엔드의 `/health`와 다음 로그를 확인합니다.

```powershell
docker compose ps
docker compose logs --tail 50 web
docker compose down
```

`down`은 서비스를 종료하고 방문자 DB 볼륨은 유지합니다. `down -v`는 DB 볼륨까지 삭제하므로 일반 종료에 사용하지 않습니다. 재실행은 `docker compose up -d --wait`, 코드 수정 후에는 `docker compose up -d --build --wait`를 사용합니다. Docker Desktop 엔진이 실행 중일 때 동작합니다.

4181 포트를 다른 서버가 사용 중이면 그 서버를 종료하거나 다음처럼 변경합니다.

```powershell
$env:NEWS_PORT='4182'
docker compose up -d --build --wait
```

이 경우 접속 주소는 http://127.0.0.1:4182/ 입니다. 컨테이너 내부는 0.0.0.0:4173으로 수신하지만 PC의 공개 포트는 127.0.0.1에만 연결합니다.

DB는 Docker의 `visitor-data` 이름 볼륨에 저장하며 기존 로컬 `data/visitors.sqlite`와 별개입니다. 기존 쿠키의 독자 정보가 새 DB에 없으면 새 방문자로 저장을 다시 시작해야 합니다. 기존 로컬 DB를 자동 복사하지 않습니다. 쿠키는 포트로 격리되지 않으므로 같은 호스트의 로컬 서버 여러 개에서 동시에 방문자 저장 기능을 시험하면 토큰이 바뀔 수 있습니다.

컨테이너용 이미지에는 코드만 복사하고 DB·Git 정보·문서·환경 파일을 제외합니다. 컨테이너는 일반 node 사용자로 실행합니다. 청사진 HTML은 기존 `docs/design/2026-10-31/frontend-blueprint-2026-10-31.html` 파일을 직접 열어 확인하며 앱 서버는 문서 경로를 제공하지 않습니다.

컨테이너 실행 후 HTTP·방문자 쿠키·재시작 유지 검증은 다음 명령으로 다시 실행할 수 있습니다. 검증이 web 서비스를 한 번 재시작합니다.

```powershell
node scripts/verify-docker.mjs
```

## 실행

Node.js 24.19.0 이상이 필요합니다. 내장 node:sqlite를 사용합니다. 외부 패키지 설치가 필요하지 않습니다.

```powershell
npm start
```

브라우저에서 http://127.0.0.1:4173 을 엽니다. 서버는 로컬 접속만 허용합니다. 팀 공유 호스팅은 별도로 설정해야 합니다.

```powershell
npm run check
npm test
npm run build
```

`dist/`는 정적 호스팅용 결과물입니다. 화면은 HTML, CSS, JavaScript로 제공하지만 방문자 저장 기능에는 Node 서버가 필요합니다. 정적 호스팅만으로 방문자 API는 실행되지 않습니다. 해시 경로를 사용하므로 기사 상세 새로고침을 위한 별도 서버 라우팅은 필요하지 않습니다.

## 화면 확인 순서

아래 순서는 기존 샘플 화면(`/?feed=sample`)을 검토할 때 사용합니다. 기본 주소(`/`)에서는 실제 백엔드 기사 목록을 확인합니다.

1. 상단의 독자를 김하늘에서 이도윤으로 변경해 첫 기사와 추천 이유를 비교합니다.
2. 카테고리를 선택하고 기사 상세로 이동합니다.
3. 피드로 돌아와 독자와 카테고리가 유지되는지 확인합니다.
4. 새로운 독자를 선택해 이력 없는 상태의 최신순 피드를 확인합니다.
5. 하단의 팀 검토용 메뉴에서 느린 로딩, 기사 없음, 조회 실패를 선택합니다.
6. 오류 화면에서 다시 시도를 눌러 정상 피드로 복구합니다.

## 검증 결과와 제한

2026-10-29, Node.js v24.19.0에서 문법 검사, 동작 테스트 4개, 정적 빌드를 통과했습니다. 테스트는 서비스 함수의 실제 반환값을 확인합니다. 브라우저 렌더링·키보드 조작·모바일 화면·실제 클릭 테스트를 대신하지 않습니다.

2026-10-29, 로컬 서버를 실행하고 브라우저에서 첫 화면이 표시되는 것을 확인했습니다. 키보드 조작, 기사 클릭 흐름, 모바일 화면과 넘침 검증은 남아 있습니다.

익명 방문자 식별은 로컬 서버에 구현했습니다. 계정 인증, 모델 예측, 행동 이벤트 전송, 관심사 학습, 데이터 파이프라인 연결은 아직 구현하지 않았습니다. 샘플 독자의 ID와 기사의 ID, 샘플 추천 묶음 ID만 분리했습니다. 새로고침은 동일 샘플을 다시 읽고 목록 생성 시각을 갱신합니다.

## 비로그인 방문자 저장

화면 상단의 **이 브라우저에서 저장 시작**을 누르면 서버가 식별 표식을 쿠키로 발급합니다. 서버의 `data/visitors.sqlite`에는 토큰 해시, 독자 ID와 생성·최근 방문·만료 시각만 저장됩니다. 초기 관심사 선택·저장은 제외했습니다. 새로고침하거나 같은 브라우저로 재방문해도 같은 독자 ID를 불러옵니다. 쿠키에는 표식만 들어가고 DB에는 그 해시만 저장됩니다. 고정 유효기간은 30일입니다.

**방문자 표식과 서버 정보 삭제**로 현재 방문자 데이터와 쿠키를 삭제할 수 있습니다. 가상 독자 피드는 방문자 식별 기능과 별개이며 클릭·체류를 수집하지 않습니다.

실행·API·검증·배포 한계는 [비로그인 방문자 구현 문서](docs/implementation/anonymous-visitor-implementation.md)를 참고하세요.

## 피드 스크롤 복원

같은 탭에서 기사를 열고 화면의 돌아가기 또는 브라우저 뒤로 가기로 복귀하면 기존 피드·독자·카테고리와 스크롤 위치를 유지합니다. 새로고침이나 새 탭까지 위치를 영속 저장하지는 않습니다. Docker 재빌드 후 브라우저에서 상세 하단 돌아가기와 브라우저 뒤로 가기를 확인했습니다.

## 가로형 피드와 동적 카테고리

카드는 썸네일 왼쪽, 제목·요약·언론사 오른쪽으로 표시합니다. 현재 기사는 가상 데이터이며 언론사도 `사이뉴스 시연 편집부`로 표시합니다.

`GET /api/v1/categories`의 `{data: string[]}` 응답으로 카테고리를 구성합니다. 현재 로컬 서버는 샘플 카테고리를 제공합니다. 응답 실패 시 오류와 재시도를 표시합니다.

피드는 3개씩 표시하고 하단 접근 시 다음 페이지를 추가합니다. 자동 관찰을 지원하지 않으면 `기사 더 보기` 버튼을 사용할 수 있습니다. 현재 총 8개의 가상 기사를 페이지로 나누며 마지막에는 종료 안내를 표시합니다. 실제 뉴스 페이지 API와 추천 API는 연결 전입니다.

## 비로그인 좋아요

피드와 상세에서 좋아요·취소를 누를 수 있습니다. 첫 저장 전에는 30일 방문자 표식 저장을 안내하고 확인받습니다. 서버 SQLite의 likes에 실제 방문자와 기사 ID를 연결하며, 재방문·새로고침 후 유지합니다. 가상 독자 선택은 좋아요 소유자를 바꾸지 않습니다. 저장이 끝날 때까지 버튼을 잠그고 실패 시 기존 상태를 유지합니다.

GET /api/v1/likes는 현재 방문자의 기사 ID 목록을 반환합니다. POST /api/v1/likes는 {article_id, liked:boolean}을 받아 원하는 상태를 저장합니다. 동일 요청을 반복해도 중복되지 않습니다. 서버는 쿠키로 방문자를 확인하고 POST Origin을 검증합니다. 방문자 삭제·만료 정리 시 좋아요도 제거합니다. 쿠키를 잃으면 이전 좋아요와 연결할 수 없습니다.

좋아요 상태만 저장하며 좋아요·취소 이벤트 이력과 추천 모델 입력 연동은 아직 구현하지 않았습니다. 기존 클릭·체류 수집 범위는 그대로입니다. npm test에서 방문자별 분리, 서버 재시작 후 유지, 중복 요청, 취소, 삭제와 잘못된 요청을 검증합니다.

## 실제 방문자와 피드 연결

가상 독자 선택을 제거하고 GET /api/v1/feed에서 현재 쿠키의 방문자에 맞춘 피드를 받습니다. 방문자 ID를 요청 본문이나 쿼리로 지정하지 않습니다. 저장 전·쿠키 만료·좋아요 없음은 최신순으로 표시합니다. 좋아요가 있으면 해당 기사 카테고리별 좋아요 개수가 많은 순, 발행 시각 순으로 정렬합니다. 추천 근거와 strategy를 함께 반환합니다. 기사는 여전히 8개 가상 데이터이며 CTR 모델·실제 뉴스 수집·배치 추천 연결은 아닙니다.

좋아요 변경은 다시 불러오기 또는 새로고침 시 피드에 반영합니다. 읽는 동안 목록을 재정렬하지 않습니다. 서버 응답 전체를 한 번 받아 화면에서 3개씩 추가하는 방식으로, 같은 목록을 읽는 중 좋아요 변경 때문에 페이지가 중복·누락되지 않습니다. 대규모 실제 기사 API 도입 시 서버의 고정된 추천 결과와 커서 기반 페이지 처리가 필요합니다. 방문자 시작·삭제 시에는 피드를 새로 조회합니다.
